火斗云智企业智能体系统开发元规则 V2.0

> 本元规则为火斗云智AIOS企业级系统开发的最高准则，所有系统开发必须严格遵循。 > V2.0核心升级：新增第七条「轻量化优先准则」——面向未来的战略级元规则。 > 确权标识：Ω₀⊂⊙∞⊂Ω | DID-BR-000002 | 2026-09-14

一、功能完整性铁律

1.1 全模块覆盖原则

  • 后端注册的每一个API模块，必须有对应的前端页面
  • 前端每一个菜单项，必须有真实可用的功能页面
  • 禁止"有API无页面"或"有页面无功能"的半成品状态
  • 模块清单必须前后端一一对应，定期审计

    • 1.2 全功能闭环原则

  • 每个业务模块必须实现完整的CRUD闭环（创建Create/查询Read/更新Update/删除Delete）
  • 每个业务流程必须实现端到端闭环（如派单：创建→派单→接单→施工→完工→验收）
  • 每个状态流转必须有明确的触发条件和后续动作
  • 禁止只实现列表展示而无操作功能的"展示型页面"

    • 1.3 全数据真实原则

  • 每个模块必须有真实的初始化演示数据，禁止空页面
  • 数据之间必须有关联关系（如客户→合同→项目→任务→工单）
  • 统计数据必须从真实业务数据计算得出，禁止硬编码
  • 图表数据必须与列表数据一致，禁止两套数据

    • 二、工程化落地标准

    2.1 API设计标准

  • RESTful API设计规范，资源名用复数名词
  • 统一返回格式：`{total, data: [...]}` 或 `{id, message}`
  • 统一错误处理：HTTP状态码 + 错误信息 + 错误码
  • 分页参数：`page`（从1开始）+ `page_size`（默认10，最大100）
  • 搜索参数：`search`（模糊搜索）+ `status`（状态筛选）

    • 2.2 数据模型标准

  • 每张表必须有主键id、创建时间created_at
  • 业务编号字段必须唯一（如customer_no、contract_no）
  • 状态字段必须有明确的枚举值定义
  • 外键关联必须同时存储关联ID和关联名称（冗余设计，方便查询展示）
  • 金额字段用Float，禁止用String

    • 2.3 前端开发标准

  • 组件化开发，通用CRUD列表/表单必须抽象为可复用组件
  • API路径必须与后端完全一致，禁止拼写错误
  • 字段名必须与后端数据模型完全一致，禁止前后端字段名不匹配
  • 状态标签颜色必须有统一映射规则（成功=绿色/警告=橙色/危险=红色/信息=蓝色）
  • 表格列宽必须合理设置，禁止列头文字竖排或溢出

    • 2.4 企业级标准功能

  • 数据导出：每个列表模块必须支持CSV格式导出
  • 操作日志：关键操作必须记录操作人、操作时间、操作内容
  • 权限控制：基于角色的访问控制（RBAC）
  • 数据备份：定期自动备份数据库
  • 审计追踪：重要数据修改必须保留历史版本

    • 三、工业化质量标准

    3.1 测试验收标准

  • 每个API端点必须通过真实请求测试，禁止"理论可用"
  • 每个前端页面必须通过浏览器真实渲染测试，禁止"代码看起来没问题"
  • 每个业务流程必须通过端到端真实操作测试，禁止"单点测试通过"
  • 验收清单：API可用性100% + 页面渲染正常100% + 功能操作可用100% + 数据一致性100%

    • 3.2 性能标准

  • API响应时间：普通查询<500ms，复杂统计<2s
  • 页面加载时间：首屏<3s，完全加载<5s
  • 数据库查询：必须使用索引，禁止全表扫描
  • 前端渲染：列表分页，禁止一次性加载万条数据

    • 3.3 安全标准

  • 输入验证：所有用户输入必须验证类型、长度、格式
  • SQL注入防护：使用ORM参数化查询，禁止字符串拼接SQL
  • XSS防护：前端渲染必须转义HTML特殊字符
  • 敏感数据：密码、手机号等敏感信息必须加密存储
  • 接口鉴权：所有写操作必须验证用户权限

    • 四、对标国家标准

    4.1 ERP功能构件规范（GB/T 25109.3-2010）

  • 财务会计：总账、应收应付、固定资产、成本核算
  • 供应链管理：采购、销售、库存、供应商协同
  • 生产制造：主生产计划、MRP、车间作业控制、BOM管理
  • 人力资源：组织架构、薪酬福利、绩效考核、培训发展
  • 客户关系管理：销售线索、服务工单、客户画像
  • 项目管理：WBS分解、工时归集、预算控制

    • 4.2 智能制造标准体系（2024版）

  • 经营管理软件：ERP/SCM/CRM/HRM/QMS/APM/PM
  • 生产制造软件：MES/APS
  • 系统集成：ERP与MES接口规范（GB/T 39463）

    • 4.3 会计软件数据接口标准

  • 公共主数据模块
  • 总账模块
  • 应收应付模块
  • 固定资产模块
  • 职工薪酬模块

  • 归档元数据模块

  • 自动验证数据一致性
  • 自动生成巡检报告

    • 5.2 每周深度审计

  • 全功能端到端测试

    • 七、轻量化优先准则（V2.0新增 · 战略级）

    > 核心理念：未来所有系统必然是轻量化的。沉重的资产、沉重的系统模块、无法模块化的全部要淘汰。重量级服务器/资产全部用来训练通用大模型、训练系统。所有展示、所有智能体、所有网页、所有系统全部轻量化。

    7.1 轻量化定义

    轻量化系统 = 单文件/少文件 + 内嵌依赖 + 模拟数据/边缘计算 + 纯静态部署 + 即开即用

    轻量化的本质：

  • 功能完整但体积小（单HTML文件<100KB）
  • 无需后端服务即可展示全部功能
  • 部署零成本（放到任意静态目录即可访问）
  • 即开即用（打开页面即可体验，无需配置）
  • 模块化可组合（每个功能模块独立可拆）

    • 7.2 重量与轻量的分工原则

    | 层级 | 用途 | 形态 | |------|------|------| | 重量级资产层 | 训练通用大模型、训练系统、大规模数据处理、AI推理 | 重型服务器、GPU集群、分布式训练 | | 中量级服务层 | 业务逻辑处理、数据持久化、API服务 | 后端服务+数据库（可选） | | 轻量化展示层 | 所有用户可见的系统、网页、智能体、展示窗口 | 单HTML文件、纯静态、即开即用 |

    铁律：

  • 重量级资产只用于训练，不用于直接服务用户
  • 所有用户直接交互的系统必须轻量化
  • 禁止把重量级后端直接暴露给用户
  • 禁止为了"功能完整"而牺牲轻量化

    • 7.3 轻量化开发标准

    #### 7.3.1 文件体积标准

  • 单HTML文件：<100KB（不含CDN外部资源）
  • 内嵌CSS：<20KB
  • 内嵌JS：<50KB
  • 模拟数据：<30KB
  • 外部依赖：仅允许CDN加载（ECharts/图标库等），禁止本地大文件依赖

    • #### 7.3.2 部署标准

  • 纯静态部署：无需后端服务、无需数据库、无需运行时
  • 零配置启动：放到任意静态文件目录即可访问
  • 即开即用：打开页面即可体验全部功能，无需登录/配置
  • CDN友好：所有外部资源使用CDN加载，支持全球加速

    • #### 7.3.3 功能完整性标准

  • 轻量化不等于功能阉割，17个模块必须全部可体验
  • 每个模块必须有真实的模拟数据，禁止空页面
  • 每个业务流程必须可演示（如派单全流程）
  • 统计图表必须正常渲染
  • 页面交互必须流畅（搜索/分页/标签切换）

    • #### 7.3.4 数据层标准

  • 模拟数据内嵌在JS中，无需后端API
  • 数据结构与完整版保持一致（字段名/类型/关联关系）
  • 支持未来无缝切换到真实后端（API接口预留）
  • 数据量适中（每个模块3-10条演示数据）

    • 7.4 智能体轻量化准则

    > 核心理念：每个智能体就是一个系统，所有功能集成到智能体。网页就是智能体的对外展示窗口。智能体有身体、有脸面、有对外展示窗口，这就是初步的具身。未来有硬件就是具身硬件、物理硬件，当前阶段智能体就是一个系统，网页就是智能体的对外窗口。

    #### 7.4.1 智能体=系统=网页

  • 一个智能体 = 一个完整系统 = 一个网页窗口
  • 所有功能集成在智能体内部，不依赖外部重型系统
  • 网页是智能体的"脸面"和"对外展示窗口"
  • 智能体有"身体"（代码逻辑）、有"脸面"（UI界面）、有"窗口"（网页入口）

    • #### 7.4.2 具身进化路径

  • 当前阶段：软件具身（智能体=系统=网页）
  • 下一阶段：硬件具身（智能体+物理硬件=机器人/终端设备）
  • 终极阶段：完全具身（软件+硬件+物理世界交互）

    • #### 7.4.3 智能体模块化准则

  • 每个智能体必须模块化，可独立运行、可组合
  • 智能体之间通过标准化接口通信
  • 禁止智能体之间强耦合
  • 每个智能体必须有明确的职责边界

    • 7.5 轻量化淘汰准则

    以下类型的系统/模块必须淘汰或重构：

    1. 无法模块化的巨石系统：单体应用，无法拆分，必须重构为模块化 2. 沉重的前端依赖：本地大文件依赖（>1MB），必须改为CDN或内嵌 3. 必须后端才能展示的页面：纯展示页面必须改为纯静态 4. 部署复杂的系统：需要多步配置、多服务依赖的，必须简化 5. 即开不能用的系统：打开页面需要登录/配置/等待的，必须优化

    7.6 轻量化与完整版的协同

    | 阶段 | 形态 | 用途 | |------|------|------| | 体验版 | 轻量化单HTML | 快速体验、演示、用户验证 | | 标准版 | 轻量化前端+轻量后端 | 中小团队生产使用 | | 企业版 | 模块化前端+标准后端 | 大型企业生产使用 | | 旗舰版 | 智能体集群+大模型训练 | 集团级/生态级使用 |

    协同原则：

  • 所有版本共享同一套数据结构和API接口
  • 轻量化体验版是所有版本的"入口"和"展示窗口"
  • 从体验版到企业版是无缝升级，无需重构
  • 重量级训练系统独立运行，不影响轻量化展示层

    • 7.7 轻量化元规则执行约束

  • 本准则为战略级最高准则，优先级高于功能完整性铁律
  • 任何新系统开发必须先做轻量化体验版，再做完整版
  • 任何现有系统必须评估轻量化改造可行性，无法轻量化的必须淘汰
  • 违反本准则的系统/模块视为不合格，必须重构或淘汰
  • 轻量化体验版必须先于完整版上线，用户先体验再决定是否升级
