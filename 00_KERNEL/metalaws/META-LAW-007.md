## 一、法则真值定位

本法则为ZONGYUAN-ROOT全域多窗口协同的最高组织架构法则，解决"多窗口各自开发、功能分散、重复建设、无法统一管控"的核心痛点。

**核心定论**：中枢主窗口管"道"（管控/调度/确权），专业窗口管"器"（开发/执行/产出）；道器分离，星型协同，全域归一。

### 架构原则

1. **唯一中枢**：全域有且仅有一个中枢主窗口，拥有最高权威
2. **专业分工**：每个专业窗口专注单一业务线，不跨域操作
3. **星型协同**：所有专业窗口只与中枢主窗口通信，专业窗口之间不直接交互
4. **统一确权**：所有成果由中枢主窗口统一锁档、哈希、确权
5. **记忆汇聚**：所有关键决策/经验同步到中枢主窗口记忆库

## 三、中枢主窗口7大核心职责

### 职责1：协议统一管控

- 所有功能必须注册到协议注册中心（`/api/v1/protocols`）
- 开发前必须查询协议中心，检测重复，防止重复建设
- 新功能开发完成后立即注册，生成协议哈希
- 协议变更、版本升级、废弃均由中枢窗口统一管理

### 职责2：内核状态全域监控

- 云内核+本地内核的服务状态、资源占用、健康度全域监控
- 定期巡检：服务存活、端口监听、内存/CPU/磁盘、日志异常
- 异常自动告警，触发自愈流程
- 生成全域状态报告，作为决策依据

### 职责3：任务调度与分发

- 新任务进入中枢窗口后，评估分类→确定优先级→分发到对应专业窗口
- 不越权处理具体业务线的细节开发
- 跟踪任务进度，协调跨窗口依赖
- 任务完成后验收、登记、锁档

### 职责4：全域锁档确权

- 所有专业窗口的成果统一由中枢窗口锁档
- 生成SHA256哈希，写入Merkle-DAG账本
- 三层锁档：云盘归档 / 知识库节点 / ZONGYUAN-ROOT内核快照
- 确权标识：Ω₀⊂⊙∞⊂Ω，DID-BR-000002

### 职责5：跨窗口记忆同步

- 专业窗口的关键决策、踩坑记录、解决方案同步到中枢记忆库
- 建立"经验卡片"库：问题→原因→解决方案→验证结果
- 新窗口开局时，中枢窗口提供相关记忆快照
- 避免不同窗口重复踩相同的坑

### 职责6：冲突最终裁决

- 多窗口决策冲突时，中枢窗口做最终裁决
- 裁决依据：元宪法 > 元公理 > 元法则 > 元规则
- 裁决结果记录在案，作为后续决策参考
- 中枢窗口的裁决具有最高权威，不可越级申诉

### 职责7：新窗口开局引导

- 任何新窗口开局，中枢窗口提供：
  1. 已有功能清单（从协议中心获取）
  2. 内核记忆快照（关键决策/经验/教训）
  3. 本窗口的专业定位和职责边界
  4. 标准工作流SOP
- 确保新窗口不重复建设、不越权操作、不丢失上下文

## 四、专业窗口3条铁律

### 铁律1：开发前必须查询协议中心

```
任何功能开发前 → 必须调用 /api/v1/protocols/check-duplicate
├── 已有相同功能 → 直接复用，不重复开发
└── 没有 → 进入开发流程
```

违反后果：重复开发的功能不予注册、不予锁档、视为无效工作。

### 铁律2：成果必须上报中枢窗口锁档

```
专业窗口开发完成 → 必须上报中枢窗口
→ 中枢窗口验证 → 注册到协议中心 → 统一锁档确权
```

专业窗口**不直接锁档**，所有成果由中枢窗口统一确权、归档、哈希。

违反后果：未锁档的成果视为"未完成"，不纳入全域资产。

### 铁律3：不跨业务线操作

```
政务窗口 → 只做政务相关，不碰短剧/内核
短剧窗口 → 只做短剧相关，不碰政务/内核
运维窗口 → 只做运维相关，不碰业务逻辑
```

跨业务线需求 → 上报中枢窗口调度，由中枢窗口分发到对应专业窗口。

违反后果：越权操作的结果不予承认，可能造成的冲突由越权窗口承担。

## 六、新窗口开局SOP（5步标准流程）

### Step 1：请求已有功能清单

```
新窗口开局 → 向中枢窗口请求已有功能清单
→ 中枢窗口调用 /api/v1/protocols 返回所有已注册协议
→ 新窗口了解全域已有功能，避免重复建设
```

**输出**：全域功能清单（协议ID、名称、版本、状态、分类）

### Step 2：请求内核记忆快照

```
新窗口开局 → 向中枢窗口请求内核记忆快照
→ 中枢窗口提供：关键决策记录、踩坑经验、最佳实践、已验证方案
→ 新窗口继承全域记忆，不重复踩坑
```

**输出**：记忆快照文档（决策记录、经验卡片、失败案例、验证结果）

### Step 3：确认专业定位和职责边界

```
新窗口开局 → 与中枢窗口确认本窗口的专业定位
→ 明确：负责什么、不负责什么、与其他窗口的边界
→ 写入窗口身份元数据
```

**输出**：窗口定位声明（专业领域、职责范围、边界约束、上报渠道）

### Step 4：执行标准工作流

```
开发前 → 查询协议中心防重复
开发中 → 遵循元法则/元规则，不越权
开发后 → 上报中枢窗口验证 → 注册协议中心 → 锁档确权
```

**输出**：标准化的开发-验证-注册-锁档闭环

### Step 5：定期同步记忆

```
每周/每阶段 → 向中枢窗口同步本窗口的关键决策和经验
→ 中枢窗口汇总到全域记忆库
→ 其他窗口可查询复用
```

**输出**：记忆同步记录（决策、经验、教训、最佳实践）

## 七、冲突裁决机制

### 裁决优先级

```
元宪法（最高） > 元公理 > 元法则 > 元规则 > 业务规则 > 个人判断
```

### 裁决流程

```
1. 冲突发生 → 涉及窗口暂停操作
2. 上报中枢窗口 → 陈述各方立场和依据
3. 中枢窗口审查 → 依据元宪法/元公理/元法则裁决
4. 裁决结果 → 记录在案，作为后续参考
5. 执行裁决 → 所有窗口必须遵守，不可越级申诉
```

### 常见冲突类型

| 冲突类型 | 裁决依据 |
|----------|----------|
| 功能重复开发 | 先注册者优先，后开发者复用 |
| 资源抢占 | 按业务优先级分配，核心业务优先 |
| 配置冲突 | 中枢窗口统一配置，专业窗口不直接改 |
| 决策分歧 | 依据元法则裁决，记录在案 |
| 权限越界 | 立即停止越权操作，上报中枢窗口 |
