> **文档编号**: ARCH-MULTI-WRITER-20260830
> **体系归属**: ZONGYUAN-ROOT · Ω-Brainμ自治内核
> **核心问题**: 定时任务/手动会话/常驻循环/API调用多写入者并发冲突
> **解决方案**: 事件溯源 + 版本向量 + 写入仲裁 + 状态合并 + 冲突解决

## 一、问题定义

### 1.1 多写入者场景

ZONGYUAN-ROOT体系存在**四类独立写入者**，它们可能同时修改同一状态：

| 写入者 | 类型 | 触发方式 | 写入频率 | 优先级 |
|--------|------|----------|----------|--------|
| 定时进化任务 | scheduled | cron每日02:00 | 每日1次 | 0（最高） |
| 手动操作会话 | manual | 用户指令 | 实时 | 2 |
| 常驻进化循环 | daemon | 后台进程 | 每30秒 | 1 |
| API调用 | api | HTTP请求 | 按需 | 3 |

### 1.2 冲突表现

1. **状态覆盖**: 写入者A读取状态→修改→写回，期间写入者B也修改了状态，A的写回覆盖B的修改
2. **认知不同步**: 写入者A创建了模块，写入者B不知道，重复创建或假设缺失
3. **版本混乱**: 定时任务和手动操作分别生成协议，版本号冲突
4. **数据丢失**: 并发写入同一JSON文件，后写入者覆盖先写入者

### 1.3 传统方案的局限

| 方案 | 局限 |
|------|------|
| 文件锁（fcntl） | 只能防止同时写入，无法解决逻辑冲突 |
| 单一写入者 | 牺牲了多写入者的灵活性 |
| 最后写入胜出（LWW） | 可能丢失重要修改 |
| 悲观锁 | 性能差，易死锁 |

## 三、核心机制详解

### 3.1 事件溯源（Event Sourcing）

**原理**: 不直接修改状态，而是将所有变更作为不可变事件追加到日志。状态由事件日志重放得到。

**事件结构**:
```json
{
  "event_id": "0ed98e805c4ba87d",
  "event_type": "truth_update",
  "writer_id": "scheduled_001",
  "writer_type": "scheduled",
  "timestamp": "2026-08-30T07:20:00",
  "version_vector": {"scheduled_001": 1, "manual_A": 3},
  "payload": {"formula": "H=abc", "value": 42},
  "idempotency_key": "a1b2c3d4",
  "status": "applied"
}
```

**优势**:
- 完整审计轨迹：所有变更可追溯
- 状态可重放：从事件日志重建任意时间点状态
- 天然支持多写入者：事件追加无冲突
- 调试友好：可回放历史事件

### 3.2 版本向量（Vector Clock）

**原理**: 每个写入者维护一个逻辑时钟，事件携带所有写入者的时钟快照，用于检测因果关系和并发。

**关键操作**:
```python
# 递增：写入者提交事件时
vv.increment("writer_A")  # {"writer_A": 1}

# 合并：应用事件时取最大值
state_vv.merge(event_vv)  # 每个写入者取max

# 因果检测：A happens-before B
v1.happens_before(v2)  # A所有时钟 <= B，且至少一个<

# 并发检测：无因果关系
v1.concurrent(v2)  # 既不是A->B也不是B->A
```

**示例**:
```
写入者A: vv={A:1, B:0}  提交事件E1
写入者B: vv={A:0, B:1}  提交事件E2
E1和E2并发（concurrent=True）→ 需要冲突解决

写入者C: vv={A:2, B:1}  提交事件E3
E1 happens-before E3 → 无冲突，正常应用
```

### 3.3 写入仲裁（Write Arbitration）

**原理**: 所有事件进入优先级队列，由单一仲裁者线程串行应用，避免并发写入。

**优先级规则**:
```
优先级0: scheduled（定时任务，最高权威）
优先级1: daemon（常驻循环，系统状态）
优先级2: manual（手动操作，用户意图）
优先级3: api（外部调用，最低权威）
```

**仲裁流程**:
1. 事件按优先级排序
2. 同优先级按提交时间排序（FIFO）
3. 串行应用，每次应用后持久化
4. 应用失败的事件进入重试队列

### 3.4 状态合并（CRDT式）

**原理**: 对于并发事件，采用无冲突复制数据类型（CRDT）思路，保证合并结果收敛。

**合并策略**:
| 字段类型 | 合并策略 |
|----------|----------|
| 计数器 | 取最大值或求和 |
| 集合 | 取并集 |
| 字典 | 递归合并，冲突字段取优先级高的 |
| 标量值 | 最后写入胜出（LWW）+ 时间戳 |
| 版本向量 | 取每个写入者的最大值 |

### 3.5 冲突解决（Conflict Resolution）

**三级解决策略**:

```
Level 1: 自动合并（80%冲突）
  └─ 字段无重叠 → 直接合并
  └─ 字段重叠但可合并（集合/计数器）→ CRDT合并

Level 2: 优先级仲裁（15%冲突）
  └─ 字段重叠且不可合并 → 高优先级写入者胜出
  └─ scheduled > daemon > manual > api

Level 3: 人工审核（5%冲突）
  └─ 同优先级且不可合并 → 标记为conflict
  └─ 生成冲突报告，等待人工决策
```

### 3.6 进化幂等性（Idempotency）

**原理**: 相同事件多次提交，只应用一次。

**实现**:
```python
# 幂等键 = hash(event_type + payload)
idempotency_key = sha256(type + sorted_payload)[:16]

# 提交时检查
if idempotency_key in applied_keys:
    return "duplicate"  # 拒绝重复

# 应用时记录
applied_keys.add(idempotency_key)
```

**效果**:
- 网络重试不会重复应用
- 定时任务重复触发不会重复进化
- 手动操作重复提交不会重复修改

## 四、写入者兼容协议

### 4.1 写入者注册

所有写入者必须先注册，获得唯一ID和优先级：

```python
engine.register_writer(
    writer_id="scheduled_daily_0200",
    writer_type="scheduled",
    description="每日凌晨2点定时进化任务",
    priority=0  # 最高
)
```

### 4.2 事件提交协议

所有写入必须通过`submit_event`，禁止直接写状态文件：

```python
# ✅ 正确方式
event = engine.submit_event(
    event_type="truth_update",
    payload={"new_formula": "H=abc"},
    writer_id="scheduled_daily_0200",
    writer_type="scheduled"
)

# ❌ 禁止方式
with open("state.json", "w") as f:
    json.dump(new_state, f)  # 可能被其他写入者覆盖
```

### 4.3 状态读取协议

读取状态通过`get_state()`，获取合并后的最新状态：

```python
state = engine.get_state()
# {
#   "version_vector": {"scheduled": 5, "manual_A": 3},
#   "event_count": 42,
#   "merged_state": {"truth_base": {...}, "architecture": {...}},
#   "conflict_count": 2
# }
```

### 4.4 冲突处理协议

写入者提交事件后，检查事件状态：

```python
event = engine.submit_event(...)
engine.process_queue()

if event.status == "applied":
    print("成功应用")
elif event.status == "rejected":
    print(f"被拒绝，冲突于: {event.conflict_with}")
elif event.status == "conflict":
    print(f"需要人工审核: {event.conflict_with}")
```

## 八、核心结论

> **多写入者兼容进化的本质是：将"直接修改状态"转变为"提交不可变事件，由仲裁者串行应用"。**
>
> 事件溯源解决了"谁在什么时候改了什么"的可追溯问题；
> 版本向量解决了"修改是否并发"的因果检测问题；
> 写入仲裁解决了"并发修改谁先谁后"的串行化问题；
> 状态合并解决了"并发修改如何共存"的收敛问题；
> 幂等性解决了"重复提交怎么办"的安全问题。
>
> 五层机制叠加，实现了多写入者环境下的**无冲突进化**。
