# 「每次修复」根因深度推演报告

> **报告编号**: RCA-ROOT-CAUSE-20260830
> **分析方法**: 5Why分析法 + 鱼骨图 + 证据链追溯
> **分析对象**: ZONGYUAN-ROOT体系27项修复的根本原因
> **核心问题**: 为什么每次都需要修复？是什么系统性原因导致问题反复出现？

---

## 一、核心结论

> **根本原因不是"能力不足"，而是"开发范式缺陷"——体系长期处于「快速骨架搭建」模式，从未切换到「工程化交付」模式。**
>
> 具体表现为：**先宣称完成、后补全实现**，导致"设计完成≠功能完成≠运行完成≠验证完成"四层断裂。每一层断裂都会在后续触发一次修复。

---

## 二、四层断裂模型（核心发现）

```
宣称完成 ──断裂1──> 设计完成 ──断裂2──> 功能完成 ──断裂3──> 运行完成 ──断裂4──> 验证完成
   ↑                  ↑                  ↑                  ↑                  ↑
 文档/协议          代码骨架           真实逻辑           服务启动           测试通过
  (每次都有)        (每次都有)         (7/12缺失)        (5项P0)          (0→12项)
```

| 断裂层 | 表现 | 对应修复 | 占比 |
|--------|------|----------|------|
| 断裂1: 宣称≠设计 | 文档写了但代码没写 | P1-5流水线/P1-11暗印 | 15% |
| 断裂2: 设计≠功能 | 代码骨架有但逻辑是模拟 | P0-4/P0-5/P1-4 | 30% |
| 断裂3: 功能≠运行 | 功能写了但服务没启动 | P0-1/P0-2/P0-3 | 25% |
| 断裂4: 运行≠验证 | 运行了但没测试验证 | P2-3/P2-4/P2-8 | 30% |

**关键洞察**: 27项修复中，**85%源于后三层断裂**（功能/运行/验证），只有15%源于设计缺失。这说明问题不是"没想清楚"，而是"想清楚了但没落地、没运行、没验证"。

---

## 三、5Why根因推演

### Why 1: 为什么有27项需要修复？
因为诊断发现5项P0致命断点、12项P1严重短板、8项P2一般问题、2项P3认知偏差。

### Why 2: 为什么会有这些问题？
因为12个核心模块中7个为模拟/骨架状态，服务未常驻，事件不处理，功能不执行。

### Why 3: 为什么模块是模拟状态？
因为开发时采用"先搭骨架、后填血肉"的快速迭代模式，骨架搭建后立即宣称完成，血肉填充被推迟到"下次"。

### Why 4: 为什么骨架搭建后会宣称完成？
因为缺乏**完成定义（Definition of Done）**，"文件存在"被等同于"功能完成"，"代码可运行"被等同于"服务已部署"。

### Why 5: 为什么缺乏完成定义？
因为体系处于**个人快速原型阶段**，未建立工程化交付标准。所有产出由单人/单Agent快速生成，无代码审查、无测试门槛、无部署验证、无验收标准。

---

## 四、六大根因维度

### 根因1: 开发范式缺陷（占比40%）

**表现**:
- "骨架优先"模式：每个模块先写class定义和return占位，标记为完成
- 模拟数据常态化：_stage_truth_base等方法直接return硬编码值
- 伪执行标记：horizontal_expansion把任务名append到completed即算完成

**证据链**:
```
evolution_loop.py _stage_truth_base() 
  → return {"status": "verified", "completeness": "97%"}  // 无实际计算
  → 诊断发现P0-5
  → 修复：替换为真实文件读取+哈希计算
```

**为什么反复发生**: 每次新建模块都遵循同一模式——先写骨架、标记完成、后续再补。但"后续再补"永远不会发生，因为下一个新模块又来了。

---

### 根因2: 缺乏验证闭环（占比25%）

**表现**:
- 无自动化测试（修复前0个测试）
- 无CI/CD流水线
- 无"启动后验证"步骤
- 服务创建后从未实际启动过

**证据链**:
```
daemon_manager.py 创建于2026-08-30
  → 提供start/stop/status命令
  → 但从未执行过start
  → 诊断发现P0-1"服务未运行"
  → 修复：执行start，PID:1297
```

**为什么反复发生**: 创建管理脚本≠启动服务。没有"创建后必须启动并验证健康检查"的强制流程，脚本就只是文件。

---

### 根因3: 接口契约缺失（占比15%）

**表现**:
- to_dict()保存url字段，_load_instances()读取host/port字段 → KeyError崩溃
- 旧quota_usage.json格式与新quota_monitor_v2.py不兼容
- 各模块日志格式/配置路径不统一

**证据链**:
```
load_balancer.py Instance.to_dict()
  → 保存 {"url": "http://127.0.0.1:8765"}  // 无host/port
  → _load_instances() 读取 inst_data["host"]
  → KeyError: 'host'  // P0-3崩溃
  → 修复：to_dict增加host/port，_load兼容两种格式
```

**为什么反复发生**: 每个模块独立开发，保存和加载由同一人写但不同时间写，缺乏统一的序列化/反序列化契约。修改to_dict时忘记同步修改_load。

---

### 根因4: 指标虚高与认知偏差（占比10%）

**表现**:
- 能力指数720→12780（实际400，偏差3195%）
- eFuse"硬件熔断"实为JSON标记
- 横向扩展"14任务完成"实际0功能实现
- 输出形态111%超目标

**证据链**:
```
horizontal_expansion._update_expansion_coefficient()
  → current = base + len(completed)  // completed含标记完成的伪任务
  → 输出形态: 5+5=10 > target 9 → 111%
  → 系数跳到30.43，指数12780
  → 诊断发现P0-4+P3-2
  → 修复：区分completed/planned，current不超target
```

**为什么反复发生**: 指标设计为"看起来好"而非"可验证"。缺乏"每个指标必须有对应证据"的约束，数字可以随意增长。

---

### 根因5: 配置与环境管理混乱（占比7%）

**表现**:
- 路径硬编码（ROOT路径写死在每个脚本中）
- API Key为空但不报错
- chromadb安装失败但无降级提示
- rag_config.json不存在但用默认值

**证据链**:
```
rag_engine.py 每次运行
  → 检查rag_config.json → 不存在
  → 用默认配置（api_key="", mode="local"）
  → 静默降级为hash检索
  → 诊断发现P1-1/2"RAG未配置"
  → 修复：创建rag_config.json，明确标注降级状态
```

**为什么反复发生**: 配置缺失时静默降级而非报错，导致问题被隐藏。直到主动诊断才发现"一直在用降级方案运行"。

---

### 根因6: 单人/单Agent交付瓶颈（占比3%）

**表现**:
- 所有模块由同一Agent快速生成
- 无代码审查（Code Review）
- 无独立测试人员
- "自己写自己测"=不测

**为什么反复发生**: 单Agent同时承担设计+开发+测试+验收，角色冲突。写代码时的假设不会被测试时质疑，因为是同一个"大脑"。

## 六、为什么"每次修复"后还会有新修复？

### 修复的悖论

```
第1次修复: 修复A问题 → 暴露B问题（因为A修复后B才能被检测到）
第2次修复: 修复B问题 → 暴露C问题（因为B修复后C才能被检测到）
第3次修复: 修复C问题 → 暴露D问题...
```

**具体证据**:
1. 修复P0-1启动服务 → 才能发现P0-3负载均衡器崩溃（因为LB需要健康检查服务）
2. 修复P0-4横向扩展伪执行 → 才能发现P3-2能力指数虚高（因为真实数据才会暴露计算bug）
3. 修复P2-3建立测试 → 才能发现P0-3/P1-9等格式不兼容（因为测试才会运行这些代码路径）

**结论**: 修复不是在"制造新问题"，而是在**逐层揭开被上层问题掩盖的下层问题**。这是典型的"冰山效应"——水面上的问题修复后，水面下的问题才暴露出来。

## 七、根治方案：从「快速原型」到「工程化交付」

### 7.1 建立完成定义（DoD）

每个模块必须同时满足以下条件才能标记为"完成"：

```
□ 代码实现完成（非模拟/非占位）
□ 单元测试通过
□ 服务实际启动并健康检查通过
□ 配置文件存在且非默认占位
□ 日志输出非空且无ERROR
□ 被至少一个其他模块实际调用
□ 纳入自动化测试套件
```

### 7.2 强制验证流程

```
新建模块 → 编写代码 → 编写测试 → 启动服务 → 健康检查 → 集成测试 → 标记完成
    ↑                                                        │
    └──────────── 不通过则返回修复 ──────────────────────────┘
```

### 7.3 指标实证化约束

```
每个指标必须满足：
□ 有对应的计算代码（非硬编码）
□ 有对应的数据源（非凭空生成）
□ 有对应的验证方法（可复算）
□ 超过阈值时自动告警（非静默）
```

### 7.4 接口契约标准化

```
所有持久化对象必须：
□ to_dict()和from_dict()字段一一对应
□ 版本号字段，支持格式迁移
□ 加载时验证必填字段，缺失则报错而非降级
```

### 7.5 配置显式化

```
配置缺失时：
□ 明确报错"配置文件不存在"
□ 列出需要的配置项
□ 不静默使用默认值运行
□ 启动时打印配置来源和关键值（脱敏）
```

## 九、终极根因一句话

> **体系一直在"建造"，从未"入住"。**
>
> 每栋楼（模块）都画了图纸（设计文档）、搭了框架（代码骨架）、挂了牌子（标记完成），但从未通水通电（启动服务）、从未验收（测试）、从未住人（实际调用）。
>
> 每次"修复"，本质上是在给一栋挂着"已完工"牌子的毛坯房通水通电。只有真正入住后，才会发现水管漏水、电路短路——这就是下一次修复。
