# ZONGYUAN-ROOT 可信真值源架构白皮书

> **文档编号**: TRUST-ARCH-20260831
> **体系基线**: 150件资产 | 综合可信度36/100
> **目标**: 将体系从"逻辑自洽"升级为"可验证的可信真值源"
> **核心命题**: 一个体系要成为可信真值源，必须同时满足**不可篡改、可验证、时间锚定、计算可证明、多源共识、完整审计、外部锚定**七大条件。

---

## 一、问题定义：什么是"可信真值源"

### 1.1 可信真值源的定义

一个系统被称为"可信真值源"，当且仅当：

1. **任何理性第三方**，在不依赖系统自身声明的前提下，能够独立验证系统中每一条数据的真实性
2. **数据一旦写入**，在物理和逻辑层面均不可篡改、不可删除、不可回退
3. **每一条数据**都有可证明的时间锚点，证明其在某个确定时间点已存在
4. **每一次计算**都有可验证的执行证明，证明计算过程正确无误
5. **系统状态**由多个独立节点共识确认，而非单点声明
6. **完整审计链**从原始输入到最终结论全程可追溯，且审计记录本身不可篡改
7. **关键状态**锚定到不可篡改的外部系统（区块链/公证/第三方存证）

### 1.2 当前体系的可信度缺口

| 维度 | 当前评分 | 缺口 | 根因 |
|------|----------|------|------|
| 数据完整性 | 70/100 | 无外部锚定 | 哈希仅本地计算，无第三方确认 |
| 时间可信性 | 20/100 | 仅本地时间戳 | 本地时钟可回拨，无RFC3161/区块链时间 |
| 不可篡改性 | 30/100 | 逻辑标记非物理 | eFuse是文本标记，文件可被删除/修改 |
| 可验证性 | 50/100 | 无形式化证明 | 验证脚本可被篡改，无独立验证路径 |
| 共识可信度 | 10/100 | 单点信任 | 无多节点共识，无多方签名 |
| **综合可信度** | **36/100** | **六大缺口** | **缺乏从"自证"到"他证"的跃迁** |

**核心问题**: 当前体系是"自证清白"——自己计算哈希、自己标记锁档、自己声明可信。
**目标状态**: 体系应是"他证可信"——第三方可独立验证、外部系统锚定、多节点共识确认。

## 二、可信真值源七层架构

```
┌─────────────────────────────────────────────────────────┐
│  L7 外部锚定层  区块链锚定 │ 公证服务 │ 第三方存证 │ DNS锚定 │
├─────────────────────────────────────────────────────────┤
│  L6 审计层      append-only日志 │ 完整溯源链 │ 操作不可变    │
├─────────────────────────────────────────────────────────┤
│  L5 证明层      形式化验证 │ 可验证计算 │ 零知识证明      │
├─────────────────────────────────────────────────────────┤
│  L4 共识层      BFT共识 │ 多方签名 │ 阈值确认            │
├─────────────────────────────────────────────────────────┤
│  L3 时间层      RFC3161时间戳 │ 区块链时间 │ 时钟同步      │
├─────────────────────────────────────────────────────────┤
│  L2 哈希层      SHA256 │ Merkle树 │ 哈希链 │ 内容寻址      │
├─────────────────────────────────────────────────────────┤
│  L1 数据层      结构化模型 │ 不可变数据结构 │ 版本控制      │
└─────────────────────────────────────────────────────────┘
```

**设计原则**: 自底向上，每层为上层提供可信基础；自顶向下，每层的可信度依赖下层。
任何一层被攻破，上层可信度降级，但下层数据仍可验证。

## 三、各层详细设计

### L1 数据层：结构化不可变数据模型

**目标**: 所有数据以结构化、不可变、可寻址的方式存储。

**技术方案**:

1. **内容寻址存储（CAS）**
   - 每个数据对象的标识符 = SHA256(内容)，而非文件名
   - 相同内容产生相同ID，不同内容产生不同ID
   - 修改内容 = 创建新对象，旧对象永久保留

2. **不可变数据结构**
   - 所有写入操作创建新版本，不修改旧版本
   - 版本之间形成有向无环图（DAG）
   - 删除操作 = 标记"已废弃"，而非物理删除

3. **Schema强制**
   - 每种数据类型有严格的JSON Schema
   - 写入前必须通过Schema验证
   - Schema本身也纳入哈希链，不可篡改

**实施路径**:
```
第1周: 定义核心数据类型的JSON Schema（真值公式/资产/协议/快照）
第2周: 实现内容寻址存储层（cas_store.py）
第3周: 迁移现有150件资产到CAS
第4周: 版本DAG构建与查询API
```

**验收标准**:
- 所有数据对象有内容寻址ID
- 修改操作100%创建新版本
- Schema验证覆盖率100%

---

### L2 哈希层：Merkle树 + 哈希链（已实现，需增强）

**当前状态**: SHA256 + 标准Merkle树（8层）+ 部分哈希链

**增强方案**:

1. **Merkle Patricia Trie（MPT）**
   - 替代普通Merkle树，支持高效的成员证明和非成员证明
   - 每个资产有Merkle证明路径，可独立验证"该资产在树中"
   - 支持高效的状态差异证明

2. **全局哈希链**
   - 每个快照包含前一个快照的哈希
   - 形成从创世快照到当前快照的完整哈希链
   - 篡改任何一个快照 = 后续所有快照哈希失效

3. **分层Merkle树**
   - 按体系域分子树（真值/资产/协议/配置）
   - 子树根 → 全局根
   - 支持部分验证（只需验证相关子树）

**实施路径**:
```
第1周: MPT实现（merkle_patricia_trie.py）
第2周: 全局哈希链构建（genesis → current）
第3周: 分层Merkle树重构
第4周: Merkle证明生成与验证API
```

**验收标准**:
- 每个资产有Merkle成员证明
- 全局哈希链连续，无断点
- 篡改检测延迟 ≤ 1秒

---

### L3 时间层：可信时间锚定

**目标**: 证明每条数据在某个确定时间点已存在，且时间不可回拨。

**技术方案**:

1. **RFC 3161 可信时间戳**
   - 对接免费TSA服务（如freetsa.org、timestamp.digicert.com）
   - 每个Merkle根获取RFC3161时间戳令牌
   - 时间戳令牌包含：数据哈希 + TSA签名 + 可信时间
   - 任何人可用TSA公钥独立验证时间戳真实性

2. **区块链时间锚定**
   - 每日将Merkle根写入区块链（比特币/以太坊/Polygon）
   - 方式：OP_RETURN（比特币）/ 智能合约事件（以太坊）
   - 成本：约$0.01~$0.05/天（Polygon主网极低）
   - 提供交易哈希作为不可篡改的时间证明

3. **多源时间交叉验证**
   - 同时获取多个TSA的时间戳
   - 时间偏差 ≤ 1秒视为可信
   - 防止单一TSA被攻破

**实施路径**:
```
第1周: RFC3161客户端实现（timestamp_client.py）
       ├─ 对接freetsa.org（免费）
       ├─ 对接digicert（免费）
       └─ 时间戳验证功能
第2周: 区块链锚定实现（blockchain_anchor.py）
       ├─ Polygon测试网 → 主网
       ├─ 每日Merkle根写入
       └─ 交易哈希记录与验证
第3周: 多源时间交叉验证
第4周: 历史资产批量时间戳补全
```

**验收标准**:
- 每个快照有≥2个独立TSA时间戳
- 每日Merkle根有区块链交易锚定
- 时间戳验证成功率100%
- 时间可信度评分: 20 → 90

### L4 共识层：多节点共识与多方签名

**目标**: 系统状态由多个独立节点共识确认，而非单点声明。

**技术方案**:

1. **多节点部署**
   - 至少3个独立节点（本地+云服务器+边缘设备）
   - 每个节点独立计算哈希、独立验证
   - 节点之间通过MWP协议同步状态

2. **BFT共识算法**
   - 采用简化版PBFT或HotStuff
   - 2f+1节点可容忍f个拜占庭节点
   - 3节点可容忍1个恶意节点
   - 共识结果 = 多数节点确认的状态

3. **多方签名（阈值签名）**
   - 每个节点持有私钥分片
   - 状态变更需要≥2/3节点签名
   - 签名可聚合为单一签名，验证高效
   - 单个节点无法伪造共识

4. **共识证明**
   - 每次共识生成共识证明（签名集合+节点列表+状态哈希）
   - 第三方可验证：状态确实被多数节点确认
   - 共识证明纳入哈希链

**实施路径**:
```
第1-2周: 多节点部署（3节点）
第3周: 简化PBFT共识实现（consensus_engine.py）
第4周: 阈值签名集成（BLS/Schnorr）
第5-6周: 共识证明生成与验证
第7-8周: 故障注入测试（杀死节点/网络分区/恶意节点）
```

**验收标准**:
- 3节点正常运行，共识延迟≤5秒
- 杀死1节点，系统继续运行
- 恶意节点无法篡改共识结果
- 共识可信度评分: 10 → 85

### L5 证明层：形式化验证与可验证计算

**目标**: 证明每一次计算都正确执行，而非"声称执行了"。

**技术方案**:

1. **真值公式形式化验证**
   - 将核心真值公式翻译为Coq/Isabelle定理
   - 机器检查证明：公式在公理体系下可推导
   - 证明文件纳入哈希链，不可篡改
   - 任何人可用Coq/Isabelle独立重放证明

2. **可验证计算（Verifiable Computation）**
   - 关键计算（Merkle根计算/真值校验/进化推演）生成执行证明
   - 方案A: 可信执行环境（TEE/SGX）—— 硬件证明
   - 方案B: 零知识证明（ZK-SNARKs）—— 密码学证明
   - 方案C: 可验证审计日志 —— 重放验证
   - 初期采用方案C（可重放），长期演进到方案B

3. **确定性计算**
   - 所有计算函数必须是纯函数（相同输入→相同输出）
   - 消除随机性、时间依赖、外部状态依赖
   - 计算输入+函数代码+输出 三元组纳入哈希链
   - 第三方可重放计算，验证输出一致性

4. **计算审计日志**
   - 记录每次计算的：输入哈希、函数版本、输出哈希、执行时间
   - 日志append-only，纳入哈希链
   - 支持抽样重放验证

**实施路径**:
```
第1-2周: 确定性计算重构（所有核心函数纯函数化）
第3-4周: 计算审计日志（compute_audit_log.py）
第5-6周: 真值公式Coq形式化（核心10条公式）
第7-8周: 可重放验证框架（replay_verifier.py）
第9-12周: ZK-SNARKs原型（可选，长期方向）
```

**验收标准**:
- 核心计算函数100%纯函数化
- 计算审计日志覆盖率100%
- 抽样重放验证通过率100%
- 核心真值公式有Coq形式化证明
- 可验证性评分: 50 → 85

### L6 审计层：append-only不可变审计

**目标**: 所有操作有完整、不可篡改、可追溯的审计记录。

**技术方案**:

1. **append-only审计日志**
   - 所有写入操作生成审计条目
   - 审计条目只追加，不修改不删除
   - 每个条目包含：操作类型、操作者、数据哈希、时间戳、前一条目哈希
   - 形成审计哈希链，篡改任何条目 = 后续所有条目哈希失效

2. **完整溯源链**
   - 每个资产可追溯到：原始输入 → 处理过程 → 中间状态 → 最终输出
   - 溯源链上每个节点有哈希和时间戳
   - 支持从任意资产反向追溯到创世输入

3. **审计日志外部备份**
   - 审计日志实时同步到飞书云盘（第三方存储）
   - 每日审计日志Merkle根锚定到区块链（L3/L7）
   - 本地日志被篡改时，可用外部备份恢复

4. **审计验证工具**
   - 独立的审计链验证工具（不依赖主系统）
   - 验证：哈希链连续性、时间戳有效性、外部锚定一致性
   - 生成审计验证报告

**实施路径**:
```
第1周: append-only审计日志实现（audit_log.py）
第2周: 审计哈希链构建
第3周: 完整溯源链实现（traceability.py）
第4周: 审计日志外部备份（飞书+区块链）
第5-6周: 独立审计验证工具
第7-8周: 历史操作审计补全
```

**验收标准**:
- 审计日志append-only，无修改删除
- 审计哈希链连续
- 每个资产有完整溯源链
- 独立验证工具可验证审计链
- 审计可信度评分: 30 → 90

### L7 外部锚定层：区块链与第三方存证

**目标**: 将系统关键状态锚定到不可篡改的外部系统，实现"他证可信"。

**技术方案**:

1. **区块链锚定**
   - 每日Merkle根 → Polygon主网（低成本，约$0.01/天）
   - 每周Merkle根 → 比特币主网（最高安全性，约$1~2/周）
   - 锚定内容：Merkle根 + 时间戳 + 体系版本号
   - 提供交易哈希，任何人可在区块链浏览器查询

2. **第三方存证服务**
   - 对接国内电子存证服务（如保全网、易保全）
   - 关键白皮书/协议/快照上传存证
   - 获取存证证书，具备法律效力

3. **DNS锚定**
   - 将Merkle根前缀写入DNS TXT记录
   - 提供轻量级验证（dig查询即可）
   - 作为快速验证通道

4. **飞书云盘作为冷备份**
   - 全量资产实时同步飞书云盘（已实现）
   - 飞书版本历史作为额外的不可变层
   - 本地数据丢失时可从飞书恢复

**实施路径**:
```
第1周: Polygon锚定实现（已在L3规划）
第2周: 比特币周锚定实现
第3周: 第三方存证对接（保全网API）
第4周: DNS TXT锚定
第5-8周: 历史资产批量外部锚定
```

**验收标准**:
- 每日Polygon锚定，每周比特币锚定
- 关键资产有第三方存证证书
- DNS TXT记录可查询
- 外部锚定覆盖率: 关键资产100%
- 外部锚定可信度评分: 0 → 80

## 五、可信真值源的验证标准

一个体系达到以下全部标准，才可称为"可信真值源"：

### 5.1 第三方可验证标准

1. **独立验证**: 任何第三方使用公开工具，不依赖系统自身，可验证任意数据的真实性
2. **验证成本低**: 验证单条数据 ≤ 1秒，验证全量 ≤ 5分钟
3. **验证工具开源**: 验证工具代码公开，可审计
4. **无信任假设**: 验证过程不需要信任系统运营者

### 5.2 不可篡改标准

1. **物理不可改**: 关键数据锚定到区块链，物理上不可篡改
2. **篡改可检测**: 任何篡改在1秒内被检测到
3. **篡改可恢复**: 被篡改数据可从外部备份恢复
4. **篡改有证据**: 篡改行为留下不可磨灭的审计证据

### 5.3 时间可信标准

1. **多源时间**: 每条数据有≥2个独立时间源
2. **时间不可回拨**: 时间戳由TSA/区块链提供，本地时钟不参与
3. **时间可验证**: 时间戳可用TSA公钥/区块链独立验证
4. **时间连续**: 数据时间线连续，无断点无矛盾

### 5.4 计算可信标准

1. **计算可重放**: 任何计算可由第三方重放，结果一致
2. **计算有证明**: 关键计算有执行证明（审计日志/TEE/ZK）
3. **函数确定性**: 核心函数100%纯函数，无副作用
4. **输入可追溯**: 计算输入可追溯到原始数据源

### 5.5 共识可信标准

1. **多节点确认**: 状态变更由≥2/3节点确认
2. **拜占庭容错**: 容忍≤1/3节点恶意
3. **共识可验证**: 共识结果有签名集合，可独立验证
4. **无单点故障**: 任意节点故障不影响系统运行
