## 一、问题：散落的免费算力，为何用不起来？

几乎每个做 AI 应用的团队都遇到过这个困境——

- 注册了七八家大模型平台，每家送几百到几千次免费调用额度；
- 魔搭给 2000 次/天，智谱 Flash 免费无 token 费，百度千帆 ERNIE-Speed 长期免费；
- 阿里百炼新人送 7000 万 tokens（90 天有效期），腾讯元器每月 100 万 token；
- 火山方舟协作奖励每日最高 500 万 tokens，天翼星辰完全免费。

这些额度加起来理论上能撑住不小的业务量，但现实是：

1. **散落各处，无法统一调度**——每个平台鉴权方式不同（Bearer / AK+SK / appkey / JWT），模型命名各异，限流规则不一样；
2. **额度耗尽无感知**——某家触发 429 了才发现，业务直接断流；
3. **免费额度有商用边界**——魔搭声明"商用建议转阿里云百炼"，元器免费 token 限渠道，直接对外卖服务可能踩条款；
4. **每次接入都是一次性工程**——换个项目又要重新对接一遍，前面积累的 Provider 配置、降级策略、额度计数器全部作废。

**核心矛盾**：免费算力是碎片化、限时、有条件的，但业务需求是稳态、可持续、可复用的。如果不把这些碎片"固化"为一层可复用的工程资产，每次都从零开始对接，就等于在持续支付重复工程成本。

## 二、解法：可插拔 Provider 池 + 路由矩阵 + 自动降级链

我们的做法是把"接入 N 个平台"这件事从**一次性编码**变成**配置化插拔**，并在上面架一层统一调度。整体架构分四层：

```
┌─────────────────────────────────────────────────┐
│              业务请求（统一入口）                 │
│         OpenAI 兼容 POST /v1/chat/completions    │
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│           统一 OpenAI 兼容网关                    │
│   · model 字段三态解析（任务别名/Provider/模型名）│
│   · 路由矩阵查降级链 → 逐 Provider 尝试            │
│   · 额度计数 + 429 退避 + 状态账本               │
└──────────────────────┬──────────────────────────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
  ┌─────────┐   ┌──────────┐   ┌──────────┐
  │ teleai  │   │modelscope│   │  agnes   │
  │ 天翼星辰 │   │  魔搭    │   │  全模态  │
  │免费文本  │   │37模型池  │   │图文视频  │
  └─────────┘   └──────────┘   └──────────┘
```

### 2.1 可插拔 Provider 层

所有 Provider 抽象为同一种数据结构——`PROVIDERS` 字典，新增一个平台只需加一条配置：

```python
"modelscope": {
    "name": "魔搭 ModelScope",
    "base_url": "https://api-inference.modelscope.cn/v1",
    "api_key_env": "MODELSCOPE_TOKEN",
    "models": ["Qwen/Qwen3.5-27B", "deepseek-ai/DeepSeek-V4-Pro",
               "ZhipuAI/GLM-5.2"],
    "kind": "openai",
    "priority": 3,
    "quota": {"per_day_total": 2000, "per_model_per_day": 500}
}
```

凭证走环境变量，不硬编码；`kind` 字段标识协议类型（目前以 OpenAI 兼容为主）；`priority` 决定降级顺序。

### 2.2 七类任务路由矩阵

不同任务对延迟、成本、模型能力的要求完全不同。我们把任务抽象为七类，每类配一条降级链：

| 任务类型 | 首选通道 | 自动降级链 |
|---|---|---|
| `text_deep`（深度推理） | OCTOP Qwen3.5-122B | 魔搭 Qwen3.5-27B → DeepSeek-V4-Pro → GLM-5.2 → 天翼 |
| `text_light`（轻量文本） | 天翼 TeleChat3（~0.48s） | 智谱 GLM-4-Flash（~0.2s）→ 硅基流动 → Agnes |
| `code_gen`（代码生成） | OCTOP deepseek-v4-pro | 魔搭 DeepSeek-V4-Pro → 天翼 |
| `image_gen` | Agnes 图片通道 | 429 限流时排队退避 |
| `video_gen` | Agnes 视频通道 | 429 限流，不切文本通道硬凑 |
| `heartbeat`（心跳巡检） | 天翼 TeleChat3 | 任一可用通道 |
| `multimodal`（多模态输入） | Agnes agnes-3.0-flash | 魔搭 InternVL3.5 |

### 2.3 自动降级链的关键原则

- **失败快速，不重试同一 Provider**：一次调用某个 Provider 返回非 200，立刻记账并切到链上下一个，不在同一个通道上反复重试浪费额度。
- **429 退避 + 冷却**：上游返回 429（Too Many Requests），该 Provider 冷却 60 秒，冷却期内跳过；全部 Provider 都在冷却时返回 429 + `Retry-After`。
- **健康检查默认零消耗**：`GET /health` 只读状态账本，不主动发探测请求；只有 `?probe=1` 才真正 ping 一遍。

## 四、工程实践：额度计数、健康账本与降级策略

把免费算力变成稳态服务，工程上最容易踩的坑不是"接不通"，而是"接了之后怎么不崩"。以下是我们在实践中沉淀的几条硬规则。

### 4.1 额度计数器：按 Provider + 日期持久化

每个 Provider 一个独立计数器，按 `Provider|YYYY-MM-DD` 键持久化到状态账本文件（`.openai_gateway_state.json`），原子写入（tmp → replace，带线程锁）。

以魔搭为例：
- 总量阈值 2000 次/天，单模型阈值 500 次/天；
- 计数器接近阈值时自动跳过该 Provider，走降级链下一个；
- 冷却中的 Provider（如刚被 429 命中）在冷却期内也跳过。

### 4.2 健康检查与状态账本

网关维护一个轻量状态账本，每个 Provider 记录：
- `state`：UP / 未测 / 冷却中；
- `last`：上次成功调用的模型名 + 延迟；
- `cooldown_until`：冷却截止时间戳；
- `failures`：失败记录。

`GET /health` 默认只读账本（零消耗），`?probe=1` 才发起真实探测。这样日常监控不花一分钱额度。

### 4.3 失败快速降级，不重试风暴

一条铁律：**单 Provider 失败即记账降级，不重试同一 Provider**。

原因很简单——免费额度本身就是稀缺资源，在同一个已经 429 的通道上反复重试，既浪费时间又浪费配额。正确做法是立刻切到下一个 Provider，等冷却时间到了再回来。

### 4.4 最小额度原则

整个盘点 + 网关搭建过程中，我们严格控制推理调用次数：
- 魔搭 `GET /v1/models`：1 次（拉取模型清单并缓存）；
- 网关 E2E `POST /v1/chat/completions`：1 次（验证用）；
- 其余全部是 GET / OPTIONS / 404 / 405 的零消耗探测。

全流程真实推理调用合计 **1 次**，没有循环重试，没有多余探测。

## 五、治理：元法则与三层锁档

技术方案再好，如果没有治理约束，部署一次就漂移一次。我们在体系内立了一条元法则（V1.1）：

> **部署完成后必须端到端测试验证**：任何网关/通道/Provider 变更部署后，必须对 `/v1/chat/completions` 发起一次真实 OpenAI 兼容调用并确认 HTTP 200 + 非空响应，结果留档（GATEWAY-LIVE-E2E-YYYYMMDD.md），未经 E2E 验证不得对外宣称可用。

当日证据：2026-10-19 网关首次部署后 E2E PASS——Provider=teleai，模型=TeleChat3-438B-A24B，HTTP 200，延迟 1629ms，端口 18081。

配套的治理机制：
- **三层锁档**：云盘归档 / 知识库节点 / 内核快照，变更即归档；
- **状态账本持久化**：额度计数、冷却状态、Provider 健康度全部落盘，重启不丢；
- **凭证不泄露**：API Key 存环境变量或加密配置，代码和文档中绝不出现明文。

## 六、商业化与合规边界

把免费算力调度做成对外服务，必须先把边界说清楚。

### 6.1 三层服务包

| 包型 | 定价 | 适合谁 |
|---|---|---|
| P1 标准部署包 | **¥2,980 一次性**（含 5 Provider） | 中小团队 / 个人开发者，需要低成本 LLM 网关 |
| P2 定制接入包 | **¥1,000–2,000 / Provider** | 有指定平台/模型诉求的客户 |
| P3 平台托管包 | **¥998–3,998 / 月** | 需要长期稳定 API 通道的 SaaS / Agent 产品方 |

### 6.2 合规红线（必须写入合同）

1. **免费额度不承诺 100% SLA**——上游动态限流、429、额度重置是平台政策，我方只提供自动切换与预警；
2. **免费额度仅作降本增效层**——多个平台官方限定"研究/测试"用途，对外售卖时核心 SLA 必须由付费通道兜底；
3. **默认配置免费池占比 ≤60%**——超限流量自动走付费通道，避免踩平台条款；
4. **客户自备账号**——注册、实名认证、绑定支付方式由客户负责，我方不代持凭证（托管模式除外，密钥加密存储）。

### 6.3 风险预案

| 风险 | 预案 |
|---|---|
| 某免费平台停服/收紧额度 | 路由矩阵自动剔除 + 其余 Provider 接管 |
| 免费额度耗尽 | 计数器预警 → 自动切换付费兜底通道 |
| 平台条款追责（商用超限） | 免费池占比 ≤60%，超限走付费 |
| 身份未明平台 | 交付前先做平台身份确认，不接不明平台 |

## 七、结论：什么才是"长期可复用数字资产"？

回到标题——碎片化免费算力如何转化为长期可复用数字资产？

答案不是"多注册几个平台"，而是沉淀三层工程资产：

1. **可插拔 Provider 层**——把每个平台的差异收敛为一条配置，新增 Provider 不写新代码，只加配置；
2. **稳态调度机制**——路由矩阵 + 自动降级链 + 额度计数 + 健康账本，让碎片化额度变成"看起来像一个稳定服务"的入口；
3. **真值留档与治理法则**——每次变更都 E2E 验证并留档，状态账本持久化，凭证不泄露，元法则约束"不验证不上线"。

有了这三层，免费算力就不再是"今天注册明天可能过期的一次性赠品"，而是**一套可以随项目迁移、随平台增减、随业务演进的调度基础设施**。下次再做新项目，不是从零对接，而是把 Provider 字典拿过来——这才是真正的数字资产复用。
