## 〇、体系顶层架构定位（DID-BR-000002 定义）

**云端 = 智能大脑；本地 worker = 大脑的手脚。**

- **云端大脑（智能中枢）**：负责智能决策、指令派发、真值存储与进化选择。载体：飞书 Base 共享大脑（任务/资产/决策/知识台账）+ 真值网关（huodouai.com 同源上报）。
- **本地 worker（手脚）**：负责执行载荷、心跳回报、状态回写。载体：容器（docker 可用时）或降级本机进程（worker_local_process.sh）。
- **支配关系**：大脑出指令（任务台账「待部署」）→ 手脚执行（部署/运行/心跳）→ 结果回大脑（状态/真值）→ 大脑再决策。**单向支配，手脚不自决。**
- **进化归属**：一切进化（版本/参数/模式）由云端大脑发起并经锁档落账；worker 不发起进化（见第二章模型分类）。

> 此定位为本文档一切约束的总前提：worker 是被大脑支配的执行器，其进化权不在自身。

## 〇之一、中枢管控与 kill-switch（DID-BR-000002 确认 2026-09-27）

**worker 接受中枢智能管控即可；与中枢心跳同步；中枢智能保有对 worker 智能 API 通道的中断权。**

1. **管控关系**：worker 不追求自治进化、不自建自主内核；一切智能能力由中枢授予、可被中枢收回。
2. **心跳同步**：worker 持续向中枢上报心跳（现有 `node_heartbeat_*` / `worker_heartbeat_*`），中枢凭心跳判断 worker 在场与健康。
3. **中断权（kill-switch）**：中枢智能可随时**中断 worker 的智能 API 通道/指令流**——包括但不限于：停止下发新指令、拒答 worker 的智能请求、冻结任务派发。worker 不得规避、不得绕过、不得在中断后自行恢复未授权能力。
4. **语义**：中断权是"单向支配"的最强形式——大脑可以收回手脚的能力而不需要手脚同意。这与进化模型（第二章）一致：worker 是被控方。
5. **实现基线**（当前体系）：worker 的智能 API 消费能力默认关闭（降级 worker 仅心跳上报）；若未来开通"注入云端智能 API"试点，必须先登记本条款为前置约束，且中断通道（中枢侧开关）先于能力开通。

## 〇之二、Worker 云端 API 同源协议（DID-BR-000002 确认 2026-09-27）

worker 全自动调用云端 API 必须遵守：

1. **密钥加密存储（CL-2 强制）**：API 密钥不明文落盘，以 AES-256-GCM 密文存储于 `meta/worker-api-key.enc.json`（IV + 密文 + 指纹）；解密密钥（KEK）仅经环境变量 `ZR_API_ENC_KEY` 注入，不落盘。
2. **调用认证**：请求携带 `X-DID: DID-BR-000002`（同源标识）+ `X-Api-Key: <解密后的密钥>`。
3. **全自动调用**：`scripts/worker_api_call.sh` 自动完成 解密 → 调用 → 3 次重试 → 审计；失败不阻塞主流程，写入 `var/audit/worker-api-calls.jsonl`。
4. **fail-closed**：KEK 缺失/解密失败 → `API_CALL_BLOCK`，不调用任何 API（宁缺勿泄）。
5. **kill-switch 仍适用**：中枢中断权覆盖 worker 的 API 调用能力——中枢不可达或中断指令下，worker 的自动 API 调用保持受控/停止。
6. **审计留痕**：每次调用记录 key/status/retries，只记指纹与结果，不记密钥明文。
7. **密钥指纹**：`meta/worker-api-key.enc.json.sha256_fingerprint` 供校验，密钥轮换需重新加密并登记账本。

## 一、问题定义

worker 是否能够进化？本文档明确结论：

**worker 是被进化的对象，不是进化主体。** 进化者（选择压力）是智能体（决策层）；worker 自身不允许自修改（写死约束）。任何违背此边界的"自进化"实现均不得落地。

---

## 二、进化模型分类

| 模型 | 机制 | 进化主体 | 允许性 |
|---|---|---|---|
| A. 版本进化 | 智能体修改脚本/镜像 → 锁档入账 → 重新部署替换旧 worker | 智能体 | ✅ 允许（现行） |
| B. 环境适应 | 运行时检测环境，自动切换运行模式（docker 可用→容器 / 不可用→降级进程） | 运行时探针（只读判定） | ✅ 允许（只选择既定模式，不改代码） |
| C. 参数调优 | 外部（智能体）修改配置参数 → worker 下次循环生效 | 智能体 | ✅ 允许（参数须入账本登记） |
| D. 自进化 | worker 基于自身反馈修改行为/参数/代码并重载自己 | worker 自身 | ❌ 禁止（违反锁档与审计边界） |

---

## 三、为什么禁止自进化（D）

1. **违反 append-only 锁档**：HASH-LEDGER 记录每个资产版本，worker 自改代码即产生未登记的变异，破坏可追溯链。
2. **审计黑洞**：无智能体复核的自我修改，无法区分"优化"与"漂移/失控"。
3. **决策质量错位**：worker 无全局视野与价值观约束，自我调参大概率次优。
4. **级联风险**：一个自进化 worker 的变异可通过心跳/网关扩散为体系性污染。

## 四、进化流程（现行 A/B/C 标准动作）

```
智能体迭代（改脚本/算子/参数）
   → 语法校验 + 演练验证（如 start/status/stop、run 探测）
   → 全域锁档（HASH-LEDGER 追加 + 卷宗回执 + 批次根哈希）
   → 网关上报（X-DID 单头）
   → 部署替换（旧 worker 回收，新版本上线）
   → 心跳/状态回写验证
```

**每轮进化的验收标准**：
- 新版本哈希已入账本（标记事件 ID）
- 演练通过（健康检查、超时回收、上报成功）
- 旧版本可回滚（账本中留存历史哈希）

## 五、未来引入"受控自进化"的前置条件（若需）

三者齐备且经智能体审批后方可评估：

1. **反馈回路**：worker 执行结果量化为可评估信号（现仅有心跳 = 存活信号，无"表现好坏"信号）。
2. **策略参数化**：行为表达为可调参数（现行为 = 代码写死），参数域有上下界与默认值。
3. **自修改闸门**：worker 仅能"提议"参数变更（写提案文件），由智能体审核后落账本再生效——**禁止直接改代码**。

满足上述条件时，仍以**提案-审批-锁档**闭环执行，不破坏 append-only。

## 六、边界红线（写死，不可协商）

- ❌ worker 不读不改自己的脚本/镜像文件
- ❌ worker 不直接写 HASH-LEDGER、卷宗、meta 配置
- ❌ worker 不产生未经账本登记的版本
- ✅ worker 只做：执行载荷、心跳上报、环境模式选择（只读判定）
