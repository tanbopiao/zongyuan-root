## 一、设计根因

多窗口/多设备开发场景下，各节点出口IP动态变化：
- 本地笔记本（家庭宽带/公司宽带，PPPoE拨号变IP）
- 豆包云电脑（云厂商出口IP池）
- 其他开发窗口（不同会话/不同环境）
- 云服务器自身（回环/内网IP）

传统静态白名单痛点：
1. IP一变就被拦，需要手动改防火墙——频繁断联
2. 完全开放端口等于裸奔——安全风险
3. 每个窗口各自维护一份IP列表——不一致、易遗漏

核心矛盾：**既要安全（不开放给全网），又要灵活（IP变了能自动通）**。

## 二、核心真值

真值1：**身份先于IP**。认证依据是节点凭证（DID+密钥/Token），IP只是凭证的临时绑定快照，不是身份本身。
- 凭证有效 → 自动放行当前IP
- 凭证无效 → 即使IP在白名单内也拒绝

真值2：**白名单是结果不是输入**。白名单不预配置，而是节点认证成功后自动写入。
- 认证通过 → 提取出口IP → 加入临时白名单 → 放行
- 白名单有TTL，过期自动移除

真值3：**分级授权**。不同节点角色对应不同端口/API权限，不是一刀切放行所有端口。
- 管理级节点（主开发窗口）：全部端口+SSH+API
- 业务级节点（短剧产线）：仅8626/8021业务端口
- 只读级节点（监控/巡检）：仅健康检查端口

真值4：**异常即熔断**。同一凭证短时间内从多个差异IP登录，或IP归属地突变，触发告警并降级为只读。

## 三、机制架构

### 3.1 三层防线

第一层：**边缘认证层（Nginx/防火墙前置）**
- 所有外部请求先过认证端点 /auth/node-bootstrap
- 携带 DID + 节点密钥 + 时间戳 + HMAC签名
- 认证成功 → 服务端自动将源IP写入临时白名单（firewall-cmd / iptables）
- 白名单TTL：默认2小时，续期可延长

第二层：**API网关层（JWT/Token鉴权）**
- 白名单内的IP仍需Bearer Token才能调用业务API
- Token权限范围由节点角色决定（RBAC）
- 防越权：管理Token不能调业务端点，反之亦然

第三层：**内核校验层（SSG解空间治理）**
- 即使IP和Token都合法，请求内容仍需过SSG校验
- 元法则冲突、格式违规、越界参数 → 熔断拒绝

### 3.2 节点注册流程

```
新节点启动
  ↓
1. 读取本地凭证（DID-BR-000002 + 节点密钥）
  ↓
2. POST /auth/node-bootstrap
   {
     "did": "did:br:000002",
     "node_id": "NODE-LAPTOP-001",
     "node_role": "admin|business|readonly",
     "timestamp": "2026-09-12T10:00:00+08:00",
     "signature": "HMAC-SHA256(密钥, did+node_id+timestamp)"
   }
  ↓
3. 服务端验证签名
   ├─ 有效 → 提取源IP，写入firewall白名单（2h TTL）
   │         → 返回JWT Token（含角色+过期时间）
   │         → 返回当前服务器时间（防时钟偏移）
   │
   └─ 无效 → 403拒绝，记录到异常日志
  ↓
4. 节点持JWT调用业务API
  ↓
5. 节点每90分钟续期一次（重新bootstrap刷新TTL）
```

### 3.4 端口暴露策略（当前→目标态）

当前问题：36个端口中约28个绑定0.0.0.0，过度暴露。

目标态：
- **仅Nginx(80/443)对外**，所有业务端口绑定127.0.0.1
- 通过Nginx反向代理对外暴露需要的API路径
- /auth/* → 认证端点（公网可访问，用于bootstrap）
- /api/* → 业务API（需JWT+白名单）
- /admin/* → 管理端点（需管理角色JWT）
- 8626/8021/8077等内部端口 → 仅127.0.0.1监听

## 四、节点角色定义

| 角色 | node_id示例 | 权限范围 | 白名单TTL |
|------|------------|---------|-----------|
| admin | NODE-LAPTOP-001 | 全端口+SSH+管理API+锁档 | 4小时 |
| business | NODE-CLOUD-PC-001 | 业务API（8626/8021）+只读监控 | 2小时 |
| readonly | NODE-CRAWLER-001 | 仅健康检查+metrics | 1小时 |
| system | NODE-INTERNAL-* | 内部回环，不走认证 | 永久 |

## 五、异常检测规则

规则1：同一凭证5分钟内从3个以上不同/24 IP段认证 → 降级为readonly + 告警
规则2：IP归属地与历史记录差异超过1000km → 二次确认（需要额外OTP）
规则3：连续5次签名验证失败 → 该IP加入blocklist（6小时）
规则4：白名单IP在TTL过期后24小时内再次出现 → 自动续期（视为正常浮动IP）
规则5：非工作时间（00:00-06:00）管理级节点认证 → 告警但不阻断

## 六、与现有体系的融合

1. **DID体系**：复用DID-BR-000002，每个节点派生子DID（did:br:000002:node:xxx）
2. **Merkle锁档**：白名单变更记录写入审计账本，每次增删都有快照
3. **SSG层**：bootstrap请求也过SSG校验（格式+频率+凭证有效性）
4. **子域隔离**：business角色节点只能访问对应子域的API端点
5. **免费优先**：不依赖外部商业WAF/CDN，用Nginx+iptables自建

## 八、反真值（永久禁止）

1. 禁止0.0.0.0直接暴露数据库/缓存/内部服务端口
2. 禁止将IP作为唯一认证依据——IP只是临时绑定
3. 禁止白名单永久不过期——动态环境必须有TTL
4. 禁止admin节点无签名直接SSH——SSH密钥+跳板机
5. 禁止将完整业务端口暴露公网——必须走Nginx代理+鉴权
