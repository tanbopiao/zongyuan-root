## 三、三大核心改进

### 3.1 日志清理截断机制

**问题**：D-006的持久化队列采用append-only日志，无清理机制，长期运行磁盘耗尽。

**解决方案**：
- **偏移位点标记**：每个分区维护offset文件，记录已消费的段号和行号
- **分段存储**：单段满50000行自动切新段，段文件命名 `part_{pid}_seg{seg_id:04d}.log`
- **自动清理守护线程**：每小时检查一次，保留最近10个段，超出自动删除最旧段
- **故障恢复**：启动时从offset位点之后恢复未消费事件，不重复消费

**关键参数**：
```python
LOG_SEG_MAX_LINES = 50000       # 单段最大行数
LOG_MAX_SEGMENTS = 10            # 保留最大段数
LOG_CLEANUP_INTERVAL = 3600      # 清理检查间隔（秒）
```

### 3.2 KV抽象层（RocksDB / 简易文件KV双后端）

**问题**：D-006的SimpleDiskKV每个key一个文件，海量节点下文件数爆炸、IO性能差。

**解决方案**：
- **KVBackend抽象基类**：定义put/get/close统一接口
- **SimpleFileKV**：默认后端，无外部依赖，适合开发/小规模场景
- **RocksDBKV**：高性能后端，`pip install rocksdb`后自动启用
- **工厂方法create_kv_backend()**：优先检测RocksDB，不可用时自动回退简易KV
- **冷热混合Merkle树**：基于KV抽象层，热点节点内存缓存、冷节点下沉磁盘

**收益**：
- 开发环境零依赖，生产环境一键切换RocksDB
- 百万级叶子节点下，内存占用可控、IO性能提升显著
- 后续可扩展其他KV后端（Redis、LevelDB等）

### 3.3 一致性哈希分片负载均衡

**问题**：D-006按domain固定路由到分区，无法动态扩缩容，热点domain导致单分区过载。

**解决方案**：
- **ConsistentHashPartitioner**：一致性哈希环，150个虚拟节点/分区，最小化扩容时的数据迁移
- **动态扩容**：`add_partition()`方法运行时增加分片，环自动更新
- **热点监控守护线程**：每分钟检查分片负载，最大分片超过均值2倍时自动扩容（上限16分片）
- **负载报告**：`get_load_report()`输出分片数、各分片负载、总事件数、热点domain列表
- **可重入锁**：使用RLock避免嵌套调用死锁

**负载均衡策略**：
```
domain → MD5哈希 → 一致性哈希环 → 分区ID → 独立队列+工作线程
```
