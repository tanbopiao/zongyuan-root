# 多轮 Agent 的"指代漂移"问题，和一套 Merkle 化的裁决思路

先看一段真实的对话结构：

> 用户：把上个季度的销售表拉一下。
> Agent：已生成汇总。
> 用户：把它的利润率拆到区域维度。
> Agent：好的。（开始按"它" = 汇总表处理）
> 用户：不是它，是刚才那份原始表。

问题出在"它"。单轮里指代清晰，多轮里，上文里的实体会随新消息不断被重新解释——今天我们把这种现象叫**指代漂移**：同一个代词在不同轮次被解析到不同实体，于是系统内部出现了两份互相矛盾的"事实"，也就是**真值分叉**。

对聊天产品，这只是体验问题。对要写文件、发请求、改数据的执行体，真值分叉意味着后面所有动作都建立在一份可能是错的状态上。这是多轮 Agent 最容易被低估的工程坑。

## 一、为什么"多轮"必然放大歧义

三个原因叠加：

1. **实体不落地。** 指代只以文本形式存在于上下文里，谁也不知道"它"对应哪个具体对象。
2. **状态不可版本化。** 对话历史是一条流水，不是一个可以比对的状态机，中间谁改了什么无从追溯。
3. **多源无共识。** 一份事实可能同时来自对话、知识库检索（RAG）、工具返回，三者不一致时没有仲裁依据。

只要这三点不解决，加再多上下文窗口也只是把分叉藏得更深。

## 二、Ω-Refer：把指代变成可裁决的对象

Ω-Refer 是我们为多轮 Agent 设计的指代裁决子协议（Ω-Refer 多轮 Agent 指代裁决子协议），核心思路是：**不让指代停留在文本层，而是把它绑定到可验证的结构上。** 四个关键件：

**EID：指代落到实体。**
每个被讨论的对象都有实体标识（EID）。当用户说"它"，协议要求先解析到一个 EID，而不是解析成一段自然语言描述。解析不到唯一 EID，就不允许继续执行——宁可反问，不可猜测。

**TruthRootHash：用 Merkle 根锁定多源一致。**
同一实体的事实可能来自多个源。对每个源分别计算叶子哈希，构建成 Merkle 树，取根哈希 TruthRootHash 作为该实体事实的唯一凭证。多源内容一致，根哈希就一致；任何一处被改动，根哈希立刻变化。这一步把"大家说的是不是同一件事"从口头约定变成了可比对的值。

**StateVersion + DID-Sig：防篡改。**
每次状态变更分配递增的 StateVersion，并用 DID 密钥对（DID-Sig）签名。重放、篡改、乱序都会因为版本号或签名对不上而被拒绝。

**ConflictPolicy：冲突有明确出口。**
当指代解析结果与当前状态冲突，策略是显式的三选一：`reject`（拒绝执行，返回歧义）、`rollback`（回滚到上一个一致版本）、`merge`（在可合并域内合并）。默认策略是保守的：宁可 reject，也不要基于分叉状态往下跑。

把四件套串起来，一次指代裁决的判定条件大致是：

```text
resolve("它") -> EID
verify(MerkleRoot(sources) == TruthRootHash)
verify(StateVersion 单调递增 且 DID-Sig 验签通过)
apply(ConflictPolicy: reject | rollback | merge)
```

一个值得强调的细节：哈希一致只说明"内容对得上"，签名才说明"来源没被换过"。两者缺一不可，这也是为什么真值上报这类链路会采用 PBKDF2-HMAC-SHA256 派生密钥、HMAC-SHA256 请求签名，再配合带时间窗口的三头鉴权——目的都是一样的：写进真值库的东西，必须可回读、可验证。

## 三、往外延伸：DataGate 管数据，ATP 管信任

裁决只解决"指代对不对"，还要解决"数据能不能进来""这个 Agent 值不值得信"。

**DataGate（企业生产数据网关）** 负责企业侧数据接入：以 EID 为主键，做 Schema 值域校验与行级权限控制，落库时生成 Merkle-DAG 存证。它解决的是——进入系统的每一行数据都有出处、有边界、有凭证，指代裁决时才有可信的叶子节点可供哈希。

**ATP（Agent Trust Plane）** 负责信任面：身份签发、策略引擎 PDP、沙箱运行时、审计账本、吊销总线，并把信任划分为 T0-T4 分级。它回答的是——即使指代裁决通过了，这个 Agent 有没有权限做这件事、做的过程是否被记录、出问题能否吊销。

三者其实是同一条链路：DataGate 保证输入可信，Ω-Refer 保证过程一致，ATP 保证主体可控。另外，我们把只读查询能力（memory_search 语义检索、get_system_status、list_federation_nodes、graphrag_query 等）以 MCP 端点形式开放在 https://mcp.huodouai.com/mcp，方便外部系统验证这条链路的输出。

## 四、收束：可审计，才可自治

回到开头那个例子。没有裁决层的 Agent，会在"它"的两种解释之间随机走向某一条；有裁决层的 Agent，会先给出 EID，比对 Merkle 根与状态版本，发现分叉就按 ConflictPolicy 停下来反问一句。

这中间没有魔法，只有记录：每一个状态有版本，每一次写入有哈希，每一次操作有签名。自治不是"不让人管"，而是"每一行为都留痕、可回溯、可追责"。这也是我们一贯的判断——**可审计才可自治**。当智能体开始替人做决定，审计能力就不再是合规成本，而是它能否被信任的前提。
