## 1. 分布式共识协议

### 1.1 Paxos 协议

**提出者**: Leslie Lamport (1998)
**核心思想**: 第一个被严格证明正确的异步容错共识算法
**角色划分**:
- **Proposer**: 提出提案（编号+value）
- **Acceptor**: 参与决策，回应提案；半数以上接受则批准
- **Learner**: 不参与决策，获取最新提案值

**两阶段提交**:
1. **Prepare/Promise**: 抢占更低编号的提案
2. **Accept/Accepted**: 确定值

**关键不变量**: 若某值已被选定，后续提案必须采用该值

**变体**:
- Multi-Paxos: 连续决策串起来，选出稳定Leader复用同编号
- Fast Paxos: 优化延迟，允许Acceptor直接投票

**适用场景**: 强一致性要求高的分布式系统（如Chubby、Spanner）

---

### 1.2 Raft 算法

**提出者**: Diego Ongaro & John Ousterhout (2014)
**设计原则**: 可理解性（Understandability）
**核心分解**: 将共识过程分解为三个独立子问题

#### 1.2.1 Leader选举
- 随机超时机制避免选票分裂
- 任期号（Term）递增，类似Lamport逻辑时钟
- Candidate向其他节点拉票（RequestVote）
- 获得多数票成为新Leader
- 节点在一个任期内只能投一票

#### 1.2.2 日志复制
- Leader单向向Follower复制日志，不允许反向
- 日志匹配特性：相同索引和任期的条目，之前所有条目相同
- 复制状态机：相同初始状态+相同命令序列=相同最终状态

#### 1.2.3 安全性约束
- Leader完整性：已提交日志必须存在于所有更高任期Leader中
- Leader只能提交本任期日志，之前任期通过提交当前日志间接提交

**服务器状态**: Follower → Candidate → Leader

**适用场景**:  etcd、Consul、TiKV、CockroachDB

---

### 1.3 Gossip 协议

**核心思想**: 流行病传播（Epidemic Dissemination）
**传播模型**:
- **反熵模型（Anti-Entropy）**: 节点定期随机选择另一节点，交换状态差异
- **谣言模型（Rumor Mongering）**: 节点收到新信息后，主动传播给随机邻居

**关键特性**:
- 最终一致性（Eventual Consistency）
- 去中心化，无单点故障
- 容错性强，节点动态加入/退出
- 传播速度: O(log N) 轮覆盖全网
- 消息复杂度: O(log N) per rumor

**变体**:
- Push Gossip: 主动推送状态
- Pull Gossip: 主动拉取状态
- Push-Pull Gossip: 双向交换

**适用场景**: Cassandra、Redis Cluster、Consul成员管理、Prometheus服务发现

---

### 1.4 CRDT 无冲突复制数据类型

**全称**: Conflict-free Replicated Data Type
**核心思想**: 数学保证收敛，无需协调
**两大类别**:

#### 1.4.1 基于状态的CRDT（CvRDT）
- 节点间交换完整状态
- 合并操作必须满足：交换律、结合律、幂等律
- 示例: G-Counter（增长计数器）、PN-Counter、LWW-Register

#### 1.4.2 基于操作的CRDT（CmRDT）
- 节点间只传输操作
- 操作必须满足交换律（因果顺序下）
- 示例: RGA（Replicated Growable Array）、LSEQ、Logoot

**常见数据类型**:
- **计数器**: G-Counter, PN-Counter
- **寄存器**: LWW-Register, MV-Register
- **集合**: G-Set, 2P-Set, OR-Set
- **图**: 2P2P-Graph, Add-only Monotonic DAG
- **序列**: RGA, LSEQ, Logoot, Treedoc

**收敛保证**: 无论操作顺序如何，最终状态一致

**适用场景**: 离线优先应用、协同编辑（Figma、Notion）、边缘计算、分布式缓存

---

### 1.5 ZAB 协议

**全称**: Zookeeper Atomic Broadcast
**核心思想**: 主从模式的原子广播协议
**阶段**:
1. **发现（Discovery）**: 选举Leader，发现最新提案
2. **同步（Synchronization）**: Follower与Leader同步，保证一致性
3. **广播（Broadcast）**: Leader接收请求，广播给Follower，半数确认后提交

**与Raft区别**: ZAB保证主从顺序一致性，Raft更通用

**适用场景**: Apache Zookeeper、Kafka（早期版本）、HBase

---

### 1.6 Quorum 法定人数机制

**核心思想**: 读写操作只需访问多数节点，而非全部
**公式**:
- 写Quorum (W) + 读Quorum (R) > 总节点数 (N)
- 保证读写重叠，读到最新数据

**常见配置**:
- **强一致性**: W=N, R=1（写全部，读任一）
- **高可用读**: W=1, R=N（写任一，读全部）
- **均衡**: W=⌈N/2⌉, R=⌈N/2⌉（多数读写）

**变体**:
- **Sloppy Quorum**: 允许临时节点替代，保证可用性
- **Hinted Handoff**: 写入失败时暂存，后续转发

**适用场景**: Dynamo、Cassandra、Riak、分布式键值存储

## 2. 数据同步算法

### 2.1 增量同步

**核心思想**: 仅传输变更数据，而非全量复制
**变更捕获策略**:

#### 2.1.1 时间戳比对
- 记录每条数据最后更新时间（updated_at）
- 仅同步 updated_at > 上次同步时间 的数据
- 缺点: 时钟漂移可能导致遗漏

#### 2.1.2 版本号追踪
- 每条数据维护递增版本号（version）
- 仅同步 version > 本地版本 的数据
- 优点: 不受时钟漂移影响

#### 2.1.3 双因子识别机制（推荐）
- 时间戳 + 版本号双重校验
- 仅当两者均大于本地缓存值时，判定为增量更新
- 有效避免单一机制带来的时钟漂移或冲突遗漏

#### 2.1.4 日志解析
- 数据库binlog/WAL解析
- 文件系统事件（inotify/fsevents）
- 应用层操作日志（Audit Log）

**适用场景**: 大规模数据同步、数据库复制、文件同步

---

### 2.2 差分同步（rsync算法）

**核心思想**: 分块哈希匹配，仅传输变化的块
**算法步骤**:
1. **旧文件分块**: 将旧文件按固定大小（如4KB）分块
2. **计算块哈希**: 对每块计算弱哈希（滚动校验）+ 强哈希（MD5/SHA）
3. **新文件逐块匹配**: 新文件逐字节滑动窗口，匹配旧文件块哈希
4. **只传输变化块**: 未匹配的部分作为新数据传输

**性能提升**:
- 大文件小修改: 流量节省可达1000倍
- 典型场景: 1GB文件修改几十字节，仅传输几十字节

**变体**:
- ** librsync**: 流式rsync库
- **zsync**: 基于HTTP的rsync
- **acsync**: 云存储优化的rsync

**适用场景**: 文件同步、备份、代码仓库同步、大文件更新

---

### 2.3 双向同步

**核心挑战**: 两端同时修改同一数据时的冲突处理
**三向Diff算法**:

#### 2.3.1 清单追踪（Manifest Tracking）
- 每次同步后保存所有文件元数据快照（路径、mtime、size、hash）
- 作为下次同步的基准（Base）

#### 2.3.2 变更检测
- 本地与基准对比: 识别本地新增/修改/删除
- 远端与基准对比: 识别远端新增/修改/删除

#### 2.3.3 智能分类
每个文件分类为:
- **仅本地修改**: 推送到远端
- **仅远端修改**: 拉取到本地
- **两端都修改**: 冲突，需解决
- **两端都删除**: 确认删除
- **无变化**: 跳过

#### 2.3.4 冲突解决策略
- **Last-Write-Wins (LWW)**: 最后修改者胜出
- **字段级合并**: 不同字段自动合并
- **版本向量比较**: 基于因果关系判断
- **用户决策**: 提交给用户手动选择
- **保留双方**: 创建冲突副本，人工合并

**防循环机制**:
- **Echo Filtering**: 丢弃自己写入触发的Webhook事件
- **Watermark-based Delta Sync**: 记录last_successful_run时间戳
- **Correlation ID**: 关联ID追踪同步来源

**适用场景**: 多设备同步、云盘同步、分布式数据库多主复制

---

### 2.4 Delta Sync 增量同步

**核心思想**: 仅同步变更（Deltas），而非整个数据集
**实现方式**:
- 本地追踪变更，同步时仅发送修改数据
- 基于操作日志（Operation Log）重放
- 基于状态差异（State Diff）计算

**优点**:
- 高效数据传输，减少带宽
- 降低电池消耗（移动端）
- 缩短同步时间

**挑战**:
- 需要健壮的变更追踪机制
- 实现复杂度增加
- 冲突检测更困难

**适用场景**: 移动端同步、边缘设备、低带宽环境

---

### 2.5 全量同步 vs 增量同步

| 维度 | 全量同步 | 增量同步 |
|------|---------|---------|
| 传输量 | 全部数据 | 仅变更数据 |
| 实现复杂度 | 简单 | 复杂（需变更追踪） |
| 一致性保证 | 强 | 依赖变更捕获准确性 |
| 适用场景 | 初始化、小数据集 | 常规同步、大数据集 |
| 网络开销 | 高 | 低 |
| 冲突检测 | 易（全量对比） | 难（需版本控制） |

**混合策略**:
- 首次全量同步建立基准
- 后续增量同步
- 定期全量校验（Checksum Verification）修复漂移

## 3. 事件驱动同步

### 3.1 Webhook 机制

**核心思想**: HTTP回调，事件发生时主动推送
**架构模式**:
```
[外部系统] → Webhook → [Webhook Receiver] → [消息队列] → [消费者]
```

**关键设计**:

#### 3.1.1 签名验证
- HMAC-SHA256签名，防止伪造
- 时间戳+nonce防重放
- 示例: `X-Signature: sha256=<hash>`

#### 3.1.2 重试机制
- 指数退避重试（Exponential Backoff）
- 最大重试次数限制
- 死信队列（Dead Letter Queue）

#### 3.1.3 幂等性保证
- 事件ID去重
- 幂等键（Idempotency Key）
- 状态机校验

#### 3.1.4 Echo Filtering（防循环）
- 丢弃自己写入触发的Webhook事件
- 使用actor metadata、correlation ID、origin headers检测
- 双向同步必备

**适用场景**: SaaS集成、支付通知、CI/CD触发、自动化工作流

---

### 3.2 Event Sourcing 事件溯源

**核心思想**: 不存储当前状态，存储所有状态变更事件
**基本原理**:
- 每个状态变更作为不可变事件追加到事件日志
- 当前状态 = 初始状态 + 所有事件重放
- 事件是唯一真相来源（Single Source of Truth）

**优点**:
- 完整审计历史，可追溯任意时间点状态
- 易于调试，可重放事件定位问题
- 天然适配CQRS架构
- 事件可被多个消费者订阅，实现解耦

**挑战**:
- Schema演化（事件结构变更）
- 快照管理（事件过多时重放慢）
- 存储增长（事件只增不减）
- 最终一致性（读模型异步更新）

**关键概念**:
- **事件存储（Event Store）**: 追加式日志，如EventStoreDB、Kafka
- **快照（Snapshot）**: 定期保存当前状态，加速重放
- **投影（Projection）**: 从事件流派生出读模型
- **命令（Command）**: 触发状态变更的意图
- **事件（Event）**: 已发生的事实，不可变

**适用场景**: 金融系统、审计要求高的系统、复杂领域模型、微服务

---

### 3.3 CQRS 命令查询职责分离

**全称**: Command Query Responsibility Segregation
**核心思想**: 读操作和写操作使用不同模型
**架构**:
```
[写请求] → Command → [写模型] → Event → [事件总线] → [读模型] → [读请求]
```

**优点**:
- 读写独立优化（写模型规范化，读模型反规范化）
- 独立扩展（读多写少场景可单独扩展读模型）
- 复杂查询简化（读模型可预计算、预聚合）
- 与Event Sourcing天然配合

**挑战**:
- 最终一致性（读模型异步更新）
- 系统复杂度增加
- 需要事件驱动基础设施
- 调试链路变长

**适用场景**: 读写比例悬殊、复杂查询、高并发读、需要审计的系统

---

### 3.4 消息队列同步

#### 3.4.1 Apache Kafka

**定位**: 分布式事件流平台
**核心概念**:
- **Topic**: 消息分类
- **Partition**: 分区，并行度单位
- **Offset**: 消息偏移量
- **Consumer Group**: 消费者组，负载均衡
- **Broker**: 服务节点

**关键特性**:
- 高吞吐量（百万级消息/秒）
- 持久化存储（可重放）
-  exactly-once语义（事务支持）
- 流处理集成（Kafka Streams、Flink）

**适用场景**: 日志收集、用户行为追踪、大数据实时计算、CDC数据同步、事件溯源

#### 3.4.2 NATS

**定位**: 云原生消息系统
**核心特性**:
- 轻量级单二进制
- 低延迟、高消息速率
- 安全默认（TLS、认证）
- 发布/订阅、请求/回复、队列组

**JetStream（持久化层）**:
- Kafka-like功能
- Key/Value存储
- Object Store
-  Exactly-once处理

**适用场景**: 微服务通信、边缘计算、IoT、云原生应用

#### 3.4.3 RabbitMQ

**定位**: 协议最完善的传统消息代理
**核心特性**:
- AMQP 0-9-1协议
- 灵活的路由（Exchange类型: direct/topic/fanout/headers）
- 消息确认（Ack）
- 死信队列
- 延迟消息（插件）

**适用场景**: 任务队列、RPC、需要复杂路由的企业集成

#### 3.4.4 RocketMQ

**定位**: 阿里巴巴开源分布式消息中间件
**核心特性**:
- 支持事务消息
- 支持延迟消息（18个级别）
- 支持消息轨迹
- 支持消息过滤（Tag/SQL）
- 高可用（主从复制、Dledger）

**适用场景**: 电商订单、交易系统、金融支付、需要事务消息的场景

#### 3.4.5 消息队列选型矩阵

| 维度 | Kafka | NATS | RabbitMQ | RocketMQ |
|------|-------|------|----------|----------|
| 吞吐量 | 极高 | 高 | 中 | 高 |
| 延迟 | 中 | 极低 | 低 | 低 |
| 持久化 | 强 | JetStream | 强 | 强 |
| 路由能力 | 弱（Topic+Partition） | 强（Subject） | 极强（Exchange） | 中（Tag+SQL） |
| 事务消息 | 支持（Exactly-once） | 支持 | 不支持 | 支持 |
| 延迟消息 | 不支持 | 支持 | 插件支持 | 原生支持 |
| 适用场景 | 大数据、日志、事件流 | 微服务、边缘、IoT | 企业集成、任务队列 | 电商、交易、金融 |

## 4. CDC变更数据捕获

### 4.1 CDC 核心概念

**全称**: Change Data Capture（变更数据捕获）
**核心思想**: 监控数据库事务日志，实时捕获数据变更
**优势**:
- 无侵入（不影响业务数据库）
- 低延迟（秒级/毫秒级）
- 完整捕获（INSERT/UPDATE/DELETE）
- 可重放（日志持久化）

**统一变更事件结构**:
```json
{
  "before": {"id": 1, "name": "old"},
  "after": {"id": 1, "name": "new"},
  "op": "u",
  "ts_ms": 1234567890,
  "source": {"db": "mydb", "table": "users"}
}
```

---

### 4.2 Debezium

**定位**: 开源分布式CDC工具，Apache顶级项目
**支持数据源**: MySQL、PostgreSQL、Oracle、SQL Server、MongoDB、Cassandra
**核心优势**:
- 无侵入（仅读取binlog/WAL）
- 支持全量+增量同步
- 多数据源适配
- 与Kafka生态深度集成（默认输出Kafka）
- 社区活跃，文档完善

**架构**:
```
[MySQL Binlog] → Debezium Connector → [Kafka] → [下游消费者]
```

**适用场景**: 中大型分布式系统、微服务架构、数据湖建设、实时数仓

---

### 4.3 Canal

**定位**: 阿里巴巴开源MySQL增量日志解析与订阅工具
**核心原理**: 把自己伪装成MySQL slave，接收binlog推送
**优点**:
- 国内生态成熟，社区活跃
- 中文文档完善
- 支持HA部署
- 轻量级，部署简单

**缺点**:
- 只支持MySQL
- 只支持增量同步，全量需配合DataX/Sqoop
- 不支持分布式（需自行扩展）

**架构**:
```
[MySQL Binlog] → Canal Server → Canal Client → [下游系统]
```

**适用场景**: MySQL为主的系统、国内企业、缓存刷新、搜索索引更新

---

### 4.4 Maxwell

**定位**: MySQL binlog实时同步到Kafka等消息队列
**核心原理**: 伪装成MySQL slave，解析binlog
**特点**:
- 轻量级，单jar包运行
- 输出JSON格式，易于消费
- 支持Kafka、RabbitMQ、Redis、Stdout
- 支持DDL同步
- 支持bootstrap全量初始化

**适用场景**: 简单MySQL CDC场景、快速原型、中小规模系统

---

### 4.5 Flink CDC

**定位**: 基于Flink的CDC连接器，流处理一体化
**核心优势**:
- 全量+增量无缝切换（无锁读取）
- 与Flink流处理深度集成
- 支持复杂转换和聚合
-  Exactly-once语义
- 支持多数据源（MySQL、PostgreSQL、Oracle、SQL Server、MongoDB）

**架构**:
```
[MySQL Binlog] → Flink CDC Source → [Flink作业] → [下游Sink]
```

**适用场景**: 实时数仓、流批一体、复杂ETL、数据湖建设

## 5. 边缘与离线优先同步

### 5.1 Offline-First 离线优先架构

**核心思想**: 离线是默认状态，而非异常状态
**设计原则**:
1. **本地优先**: 所有读写先操作本地数据库，不等待网络
2. **后台同步**: 网络可用时自动同步变更
3. **冲突解决**: 预定义冲突解决策略，无需用户干预
4. **渐进增强**: 功能随网络质量提升

**本地存储选择**:
- **结构化数据**: IndexedDB（浏览器）、SQLite（移动端）、Realm
- **二进制文件**: OPFS（浏览器）、本地文件系统
- **HTTP响应**: Cache API（Service Worker）

**同步策略选择**:
| 策略 | 适用场景 | 复杂度 | 一致性 |
|------|---------|--------|--------|
| LWW | 简单、容忍丢失 | 低 | 弱 |
| Sync Queue | 表单式交互 | 中 | 中 |
| OT（操作转换） | 实时协同编辑 | 高 | 强 |
| CRDT | 真正离线优先 | 高 | 最终一致 |

**适用场景**: 移动应用、IoT设备、边缘计算、网络不稳定环境

---

### 5.2 边缘计算同步

**核心挑战**: 边缘设备网络不稳定、带宽有限、算力受限
**关键技术**:

#### 5.2.1 延迟复制技术（Lazy Replication）
- 边缘节点本地完整读写
- 网络恢复后高效增量同步
- 确定性冲突解决
- 适用于对抗性、间歇性、有限带宽环境

#### 5.2.2 QoS分级传输
- 关键控制消息优先传输
- 日志等低优先级数据异步发送
- 根据网络质量动态调整

#### 5.2.3 边缘本地存储
- Pod、ConfigMap等资源边缘持久化
- 断连期间仍可运行
- 心跳间隔根据网络质量调整

#### 5.2.4 分级同步策略（推荐）
根据数据重要程度分级:
- **第一类: 实时告警数据**（设备故障、安全告警）→ 准实时同步
- **第二类: 业务数据**（订单、交易）→ 分钟级同步
- **第三类: 日志/统计数据** → 批量异步同步

**适用场景**: IoT、工业互联网、智能零售、远程监控

---

### 5.3 多主复制（Multi-Master Replication）

**核心思想**: 多个节点均可读写，异步同步
**优点**:
- 高可用（任一节点故障不影响写入）
- 低延迟（就近读写）
- 水平扩展（写能力随节点增加）

**挑战**:
- 写冲突（同一数据多节点同时修改）
- 冲突解决复杂
- 最终一致性（非强一致）
- 数据漂移风险

**冲突解决策略**:
1. **LWW (Last-Write-Wins)**: 最后修改胜出（基于时间戳/版本号）
2. **字段级合并**: 不同字段自动合并
3. **版本向量**: 基于因果关系判断
4. **应用层冲突**: 业务逻辑决定
5. **人工干预**: 提交给用户

**实现系统**:
- PostgreSQL (Bucardo、BDR)
- MySQL (Group Replication、Galera Cluster)
- CouchDB、Couchbase
- DynamoDB（Global Tables）

**适用场景**: 全球分布应用、多区域部署、高可用写入、离线优先

---

### 5.4 Hub-and-Spoke 中心辐射架构

**核心思想**: 中心节点协调，边缘节点（Spoke）独立运行
**同步流程**:
1. 边缘节点断连时完整本地读写
2. 网络恢复后与中心节点执行增量同步
3. 中心节点协调冲突，广播到其他边缘节点
4. 仅传输变更状态，带宽效率高

**优势**:
- 边缘自治，断连可用
- 中心协调，全局一致
- 增量同步，带宽高效
- 确定性冲突解决

**适用场景**: 零售门店、分支机构、分布式团队、边缘计算集群

---

## 6. 逻辑时钟与版本控制

### 6.1 Lamport 逻辑时钟

**提出者**: Leslie Lamport (1978)
**核心思想**: 为事件分配单调递增数字，捕捉偏序关系
**算法规则**:
1. **本地事件**: 执行内部事件或发送消息前，计数器+1
2. **消息发送**: 发送消息时附带当前计数器值
3. **消息接收**: 收到消息时，设置本地计数器 = max(本地值, 收到值) + 1

**保证**: 若 a → b（a因果先于b），则 timestamp(a) < timestamp(b)
**局限**: 反向不成立——timestamp(a) < timestamp(b) 不能推出 a → b（可能是并发）

**适用场景**: 分布式事件排序、互斥算法、快照算法

---

### 6.2 Vector Clock 向量时钟

**提出者**: Colin Fidge & Friedemann Mattern (1988)
**核心思想**: 每个节点维护计数器数组，可检测并发
**算法规则**:
1. **本地事件**: V[i] ← V[i] + 1
2. **消息发送**: 附带当前向量时钟V
3. **消息接收**: 对所有j，V[j] ← max(V[j], W[j])，然后V[i] ← V[i] + 1

**比较规则**:
- **V < W**（V因果先于W）: 所有j，V[j] ≤ W[j]，且存在j，V[j] < W[j]
- **V > W**（V因果后于W）: W < V
- **V ∥ W**（并发）: 既不V < W，也不W < V

**优势**: 可精确判断因果关系和并发关系
**劣势**: 向量大小随节点数增长，通信开销大

**适用场景**: 分布式数据库（Riak、Dynamo）、协同编辑、冲突检测

---

### 6.3 Hybrid Logical Clock (HLC) 混合逻辑时钟

**核心思想**: 结合物理时钟和逻辑时钟，兼顾因果排序和真实时间
**结构**: `(physical, logical)` 两部分
**算法规则**:
1. **本地事件**: 
   - l.physical = max(l.physical, current_physical_time)
   - 若 l.physical == previous.physical，则 l.logical++，否则 l.logical = 0
2. **消息接收**:
   - l.physical = max(l.physical, msg.physical, current_physical_time)
   - 若 l.physical == max(previous.physical, msg.physical)，则 l.logical = max(previous.logical, msg.logical) + 1
   - 否则 l.logical = 0

**优势**:
- 单值大小，不随节点数增长
- 保持因果排序（a → b ⇒ HLC(a) < HLC(b)）
- 接近真实物理时间，可用于时间范围查询
- 容忍时钟漂移（NTP同步误差内）

**适用场景**: 分布式数据库（CockroachDB、MongoDB）、全局快照、事务排序

---

### 6.4 版本向量（Version Vector）

**核心思想**: 跟踪每个副本的更新次数，用于冲突检测
**与Vector Clock区别**:
- Version Vector跟踪副本更新，用于副本间同步
- Vector Clock跟踪事件因果，用于事件排序
- 算法相似，但用途不同

**应用**:
- 分布式文件同步（Rsync、Syncthing）
- 分布式数据库（Riak、Dynamo）
- 离线优先应用

---

### 6.5 时钟方案对比矩阵

| 维度 | Lamport | Vector Clock | HLC | 物理时钟(NTP) |
|------|---------|--------------|-----|---------------|
| 因果排序 | ✓ | ✓ | ✓ | ✗ |
| 并发检测 | ✗ | ✓ | 部分 | ✗ |
| 真实时间 | ✗ | ✗ | ✓ | ✓ |
| 空间开销 | O(1) | O(N) | O(1) | O(1) |
| 时钟漂移容忍 | ✓ | ✓ | ✓ | ✗ |
| 全局唯一排序 | ✗ | ✗ | 部分 | ✗ |
| 适用场景 | 简单排序 | 冲突检测 | 数据库事务 | 时间戳 |

## 7. 同步规则与最佳实践

### 7.1 同步设计铁律

1. **幂等性**: 同步操作可重复执行，结果一致
2. **可重放**: 同步日志可重放，修复数据漂移
3. **断点续传**: 中断后可从断点继续，无需全量重来
4. **冲突可检测**: 并发修改必须能被检测到
5. **冲突可解决**: 预定义冲突解决策略，无需人工干预
6. **可观测**: 同步状态、延迟、错误可监控
7. **可回滚**: 同步错误可回滚到之前状态

### 7.2 双向同步防循环规则

1. **Echo Filtering**: 丢弃自己写入触发的事件
2. **Correlation ID**: 每个同步操作带唯一关联ID
3. **Watermark**: 记录last_successful_run时间戳
4. **Actor Metadata**: 标识写入来源，过滤自身
5. **Origin Headers**: HTTP头标识请求来源

### 7.3 冲突解决优先级

1. **字段级合并**（不同字段）→ 自动合并
2. **因果关系判断**（版本向量）→ 因果后者胜出
3. **LWW**（时间戳/版本号）→ 最后修改胜出
4. **业务规则**（应用层逻辑）→ 业务优先级决定
5. **人工干预**（无法自动解决）→ 提交用户决策

### 7.4 同步质量监控指标

- **同步延迟**: 事件发生到同步完成的时间
- **同步成功率**: 成功同步数/总同步数
- **冲突率**: 冲突数/总同步数
- **数据漂移率**: 两端不一致数据占比
- **重试次数**: 平均重试次数
- **死信队列长度**: 未处理失败消息数

### 7.5 分级同步策略（推荐）

| 数据级别 | 同步方式 | 延迟要求 | 一致性要求 |
|---------|---------|---------|-----------|
| 实时告警 | 准实时推送 | <1秒 | 强一致 |
| 核心业务 | 增量同步 | <1分钟 | 最终一致 |
| 统计数据 | 批量同步 | <1小时 | 最终一致 |
| 日志归档 | 异步批量 | <24小时 | 弱一致 |
