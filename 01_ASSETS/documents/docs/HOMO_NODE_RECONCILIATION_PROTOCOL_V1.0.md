# 同源节点对账协议 V1.0

**确权锚点**: Ω₀⊂⊙∞⊂Ω | DID-BR-000002 | Ω-TAN-7-001
**协议版本**: V1.0
**生效时间**: 2026-09-10

---

## 一、协议目的

建立同源节点之间的身份互认、状态对账、资源共享、冲突检测机制，确保多节点协同工作时不重复、不冲突、不漂移。

---

## 二、节点身份定义

### 2.1 节点类型

| 节点类型 | 说明 | 职责 |
|---------|------|------|
| **主根节点** | 云端内核中枢 | 全局调度、真值锚定、仲裁 |
| **本地节点** | 本地PC/工作站 | 开发调试、本地算力、仿真测试 |
| **云Worker节点** | 云服务器执行节点 | 任务执行、算力提供、产线生产 |
| **边缘节点** | 边缘设备 | 数据采集、轻量推理、实时响应 |

### 2.2 节点身份凭证

每个节点必须携带以下双标识：
- `DID`: DID-BR-000002（体系身份）
- `ROOT_OMEGA`: Ω-TAN-7-001（主权根）
- `NODE_ID`: 节点唯一ID（如 `node-cloud-main-001`）
- `NODE_TYPE`: 节点类型
- `CAPABILITIES`: 能力清单（如 `["text_generation", "image_generation", "video_generation"]`）

## 三、握手对账流程

### 3.1 节点注册

新节点接入时，向主根节点发送注册请求：

```json
{
  "action": "register",
  "node_id": "node-local-pc-001",
  "node_type": "local",
  "capabilities": ["text_generation", "code_execution"],
  "resources": {
    "cpu_cores": 8,
    "memory_gb": 32,
    "gpu": "RTX 3060 12GB"
  },
  "version": "v2.3.0",
  "timestamp": 1757500000
}
```

主根节点验证通过后，返回：
```json
{
  "status": "registered",
  "node_id": "node-local-pc-001",
  "assigned_role": "local_development",
  "heartbeat_interval": 30,
  "sync_endpoint": "http://cloud-main:8080/api/sync"
}
```

### 3.2 心跳保活

节点每30秒发送心跳：
```json
{
  "action": "heartbeat",
  "node_id": "node-local-pc-001",
  "status": "healthy",
  "load": {"cpu": 25, "memory": 40},
  "active_tasks": 2,
  "timestamp": 1757500030
}
```

### 3.3 状态对账

主根节点定期（每5分钟）发起全节点状态对账：

1. 收集所有节点的状态快照
2. 对比资源占用、任务分配、版本一致性
3. 检测重复工作、冲突任务、资源浪费
4. 生成对账报告，发送优化建议

---

## 四、资源调度规则

### 4.1 任务分配优先级

1. **本地优先**: 本地节点能处理的任务，优先分配给本地
2. **能力匹配**: 根据节点能力清单分配任务
3. **负载均衡**: 优先分配给负载较低的节点
4. **成本最优**: 免费资源优先，付费资源需人工审核

### 4.2 重复工作检测

- 同一任务ID只能在一个节点执行
- 相同输入的任务，结果可复用，不重复执行
- 节点间通过主根节点协调，避免冲突

---

## 五、冲突解决机制

### 5.1 冲突类型

| 冲突类型 | 说明 | 解决方式 |
|---------|------|---------|
| **资源冲突** | 多节点争抢同一资源 | 主根节点仲裁，按优先级分配 |
| **版本冲突** | 节点版本不一致 | 强制同步到最新稳定版本 |
| **数据冲突** | 同一资产被多节点修改 | 基于Merkle哈希合并，冲突部分人工审核 |
| **任务冲突** | 重复任务被多节点执行 | 取消冗余任务，保留最早启动的 |

### 5.2 仲裁流程

1. 冲突检测 → 2. 暂停相关操作 → 3. 主根节点分析 → 4. 生成解决方案 → 5. 通知相关节点 → 6. 执行解决方案 → 7. 记录审计日志

## 六、稳态校准

### 6.1 校准目标

- 所有节点版本一致
- 核心真值同步
- 资源使用最优
- 无重复工作
- 无冲突任务

### 6.2 校准触发条件

- 新节点接入
- 节点版本更新
- 检测到冲突
- 定期校准（每小时）
- 人工触发

### 6.3 校准内容

1. 版本一致性检查
2. 核心真值同步（元公理、元法则、元规则）
3. 资源占用优化
4. 重复工作清理
5. 冲突任务解决
6. 生成校准报告

---

## 七、审计与追溯

### 7.1 操作审计

所有节点操作必须记录：
- 时间戳
- 节点ID
- 操作类型
- 操作详情
- 操作结果
- 关联任务ID

### 7.2 对账报告

每次对账生成报告，包含：
- 节点清单及状态
- 资源使用统计
- 重复工作检测结果
- 冲突解决记录
- 优化建议
- 校准执行结果

---

## 八、安全约束

1. 所有通信必须携带双标识（DID + ROOT_OMEGA）
2. 异源节点请求直接拒绝
3. 敏感操作（删除数据、修改真值）必须人工审核
4. 节点间禁止直接通信，必须经过主根节点中转
5. 所有操作记录不可篡改，纳入Merkle-DAG谱系
